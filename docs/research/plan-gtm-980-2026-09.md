## 0. 先に検算する（この計画の形を決めている前提）

調査項目を並べる前に、目標そのものを数字に落とす。**ここが計画の分岐点**なので、メンバーに配る前に必ず読む。

### 0-1. 必要な有料件数

| 前提 | 必要件数 |
|---|---|
| 980円がそのまま入る（Web決済・手数料無視） | **307件** |
| App内課金・小規模事業者プログラム（手数料15%） | **361件** |
| App内課金・通常（手数料30%） | **438件** |
| 上記に加え 980円が税込 → 税抜891円で計算 | **さらに1.10倍** |

**「30万円」が売上（グロス）か手残り（ネット）かで、必要件数が1.4倍変わる。**
どちらの定義かを最初に決める。この計画では**グロス307件**を基準に置く。

### 0-2. 期間と速度

- リリース 10月中旬 → 12月31日 = **約77日**
- 307件 ÷ 77日 = **1日あたり純増4件を、年末年始も含めて毎日**

### 0-3. 個人課金（D2C）で積む場合に必要な無料ユーザー数

フリーミアム転換率を2〜5%と置くと（`20260823-pricing-plan-review.md` の前提）:

| 転換率 | 必要な無料ユーザー | 1日あたり新規登録 |
|---|---|---|
| 5% | 6,140人 | 80人/日 |
| 3% | 10,230人 | 133人/日 |
| 2% | 15,350人 | 199人/日 |

**比較対象**（`dl-target-20k-2026-09.md` より・原文未検証）:

- アグリハブ: 登録者5万人まで数年、**2万人まで約3年半** ≒ 平均16人/日
- KSAS（クボタ）: 会員26,400人まで約5年 ≒ 平均14人/日（全国販売網つき）

つまり D2C 単独の場合、**業界の実績値の5〜12倍の獲得速度を、ブランドゼロ・レビューゼロの状態から77日間維持する**設定になる。現状の本番は worker 0人・記録18件。

### 0-4. したがって、この調査の本当の問いは1つに絞られる

> **307件を「1人ずつ」集めるのか、「まとめて」集めるのか。**

まとめて集める場合の形（980円/席の団体一括）:

| 契約単位 | 席数 | 月額 | 30万円に必要な件数 |
|---|---|---|---|
| 生産部会・農業法人 | 100席 | 98,000円 | **3件** |
| 同 | 50席 | 49,000円 | **6件** |
| 同 | 20席 | 19,600円 | **16件** |

**3〜6件の団体契約なら、77日でも射程に入る。307人の個人課金は入らない。**
ただし団体側の決裁が年度予算（4月始まり）に縛られるなら、10月着手で12月課金開始は成立しない。

**→ この計画の最優先調査は「団体一括は売れるか／決裁は何ヶ月か」（WP1）。他はその後ろに並ぶ。**

## 1. この調査で決める3つの分岐

調査は「知識を集める」ためではなく、**次の3つを選ぶため**に行う。各調査パッケージは必ずどれかに紐づく。

| 分岐 | 選択肢 | 決める調査 |
|---|---|---|
| **A. 収益の形** | ①個人307件 ②団体3〜6件 ③併用 | WP1, WP2 |
| **B. 無料と有料の線** | ①機能で切る ②蓄積データの活用範囲で切る ③席数・圃場数で切る | WP3, WP4, WP5 |
| **C. 12月という期日の扱い** | ①課金開始を12月まで ②「契約内定30万円相当」を12月まで（課金開始は翌年度） | WP1, WP6 |

**Cは逃げではない。** 団体決裁が年度予算なら、12月に課金が立っていないことと事業が失敗していることは別。**どちらを成果と呼ぶかを先に決めておかないと、12月に評価できない。**

### WP1 【最優先】団体一括契約は成立するか、決裁は何ヶ月かかるか

**問い**
980円/席の団体一括（JA生産部会・農業法人・集落営農・自治体）は、実際に契約として成立するか。提案から入金までの標準的な期間は何ヶ月か。年度予算（4月始まり）に縛られるのはどの相手か。

**これで変わる判断**
分岐A（収益の形）と分岐C（期日の扱い）。**この答えが出るまで、他の施策の優先順位を決められない。**

**調べ方（一次情報）**
1. 農業向けSaaSの**団体導入の公表事例**を探す。プレスリリース・導入事例ページの原文に到達し、「契約単位（組織/席）」「導入から稼働までの月数」「価格の出し方（席単価/定額）」を抜く。対象: アグリノート、アグリハブ、KSAS、Z-GIS（JA全農）、農業日誌系の各社
2. **JAグループの新規サービス導入の決裁経路**を調べる。単協が独自に契約できるか、県連・全農の承認が要るか。AgVenture Lab（JAアクセラレーター）の採択企業がその後どう販売しているか
3. **自治体（県・市町村）のICT導入予算**の執行時期。補正予算で年度途中に付く余地があるか
4. 可能なら**実物に当たる**: 近隣のJA営農指導部門・農業法人1〜2社に、価格を出して「これは誰が決裁しますか／いつ払えますか」を直接聞く（売り込みではなく決裁構造の確認）

**成果物**
- 相手カテゴリ別の表: 決裁者の役職 / 決裁に要する月数 / 年度予算の縛りの有無 / 席単価が通じるか定額を求められるか
- **12月までに入金が成立しうる相手カテゴリの名指し**（ゼロならゼロと書く）
- 実在する候補リスト10件（団体名・所在・規模・接触経路）

**担当の適性** 営業・事業開発寄り。電話・訪問を厭わない人
**期限** 着手から**7日**（他の全パッケージの前提になるため最優先）

### WP3 農家が「払える」決済手段は何か（有料転換の物理的ボトルネック）

**問い**
基幹的農業従事者の平均年齢67.7歳・65歳以上69.6%（2025年農林業センサス）という母集団で、**クレジットカードによるApp内課金／Stripeが実際に完了できるのか。** 完了できないなら、有料転換率の議論より先にここが天井になる。

**これで変わる判断**
分岐B、および課金インフラの実装（WP6）。**「口座振替・請求書払いが要る」なら、IAP前提の料金設計そのものが崩れる。**

**調べ方**
1. 農業向けサービスの**決済手段の実態**: アグリハブ/アグリノート/KSAS等の有料プランが受け付けている決済手段（カードのみか、請求書・口座振替があるか）を料金ページ原文で確認
2. JA を通じた**購買・共済の決済慣行**（購買未収金・口座振替）。農家がJA口座からの引き落としに慣れている度合い
3. 高齢層のアプリ内課金の**離脱率に関する公開データ**（あれば）
4. **実地**: WP5のヒアリング対象に「スマホでクレカ決済をしたことがあるか／App Storeにカードを登録しているか」を必ず聞く

**成果物**
- 決済手段別の「使える見込み」判定表（カード/キャリア決済/口座振替/請求書/コンビニ）
- **団体一括の場合の請求方法**（請求書払いが必須なら、IAPではなくWeb契約になる → Apple手数料の議論が消える）

**担当の適性** リサーチ + ヒアリング
**期限** 着手から**10日**

### WP5 支払意思（WTP）の実地検証 — 農家20〜30人

**問い**
「何になら980円払うか」。現状 `ai_outputs` は全件が開発時の動作確認で、**支払意思を測るデータが存在しない**（`20260823-pricing-plan-review.md`）。

**これで変わる判断**
分岐B。**無料と有料の線を、社内の想像ではなく発言で引く**ための唯一の材料。

**調べ方**
1. **定性ヒアリング 20〜30人**（1人20分）。聞くのは機能の good/bad ではなく、**今払っているもの**:
   - 農業関係で今お金を払っているサービス・アプリは何か。月/年いくらか。誰が決めたか
   - 記録・防除・帳簿で、今いちばん時間を取られている作業は何か。年に何回か
   - （価格を見せて）980円/月は、何ができれば妥当か。**逆に、いくらなら即決か**
   - スマホで課金したことがあるか（WP3と共通）
   - 誰に勧められたら使うか（この答えがWP2のチャネル検証になる）
2. **定量**: 事前登録LP を1枚作り、WP2の各チャネルに1本ずつ流す。「無料で使う」「980円で使う」の2ボタンを置き、**有料ボタンのクリック率**を測る（決済は取らない・意図の測定）。チャネル別のCV差がそのままWP2の検証になる
3. **禁止事項**: 「この機能欲しいですか？」は聞かない（全部「はい」になる）。**過去の行動と支払い実績だけを聞く**

**成果物**
- 発言録（匿名化）と、「今払っているもの」の一覧。**金額の実績値が最重要**
- 支払意思のある機能の順位（発言の頻度ではなく、金額を口にした回数で並べる）
- LP のチャネル別 有料ボタンCTR

**担当の適性** 現場に行ける人。農家との接点がある人を優先
**期限** 着手から**21日**（並行実施。10月末までに一次報告）

### WP6 課金インフラと法務の実装要件（10月中旬リリースに間に合うか）

**問い**
マルチテナント化＋Stripe連携は未着手（`roadmap.md`）。**10月中旬リリース時点で課金は載るのか。** 載らないなら、12月までの77日はさらに短くなる。

**これで変わる判断**
分岐C（期日の扱い）。**課金開始日が11月なら、30万円到達の期間は実質1.5か月になる。**

**調べ方**
1. **App内課金（自動更新サブスクリプション）**: 審査の追加要件（App Store Review Guidelines 3.1.1・3.1.2）、価格設定・無料トライアルの設定方法、**小規模事業者プログラム（15%）の申請締切と適用開始日**（申請月の翌月適用など、適用の遅れが手取りに直結する）
2. **Stripe（Web契約）**: 日本での開設に必要な書類、個人事業主で可能か、審査期間
3. **特定商取引法に基づく表記**: 個人事業主の場合、**氏名・住所・電話番号の公開義務**の範囲と、例外（「請求があったら遅滞なく開示」の運用可否）。`20260912-release-line.md` は「個人名義で出す」と決めているので、**ここが衝突する可能性がある**
4. **インボイス制度**: 団体（法人・JA）に売るなら適格請求書発行事業者の登録が要るか。登録に要する期間
5. **消費税**: 980円が税込か税抜か。免税事業者のうちはどうなるか
6. **実装工数**: 既存の「アクセス判定を1箇所の共通関数に通す」設計（`roadmap.md` 実装順序の原則）が本当に1箇所に集約されているかをコードで確認し、課金判定への差し替え工数を見積もる

**成果物**
- **課金開始可能日（最短）** の日付。IAP経路とWeb経路の2本それぞれ
- 法務タスクのチェックリスト（誰が・いつまでに・何を提出）
- **特商法表記と「個人名義でリリース」が両立するかの判定**

**担当の適性** 開発 + 事務手続きができる人。3〜5は税理士/専門家への確認を含む
**期限** 着手から**7日**（リリース日に直結するため前倒し）

### WP7 季節性とチャーン — 12月という期日は妥当か

**問い**
「ストック収益」は**積み上げ − 解約**。日本の農業は冬に作業量が落ちる。**12月は農業記録アプリのアクティブ率が年間で最も低い時期ではないか。** そこをゴールに置くのが妥当か。

**これで変わる判断**
分岐C。および「無料枠の設計」（閑散期に解約されない理由を有料側に置けるか）。

**調べ方**
1. 農業アプリの**季節別利用の公表データ**（各社のブログ・登壇資料・ストアレビューの投稿時期分布）
2. 作業の年間分布（`agriculture` スキルの栽培暦の知識を参照）。記録が発生する月・しない月
3. **自社データ**: `reports` の作成日を月別に集計する（18件しかないが、無いよりは形が見える）
4. サブスクの一般的な**初月解約率**と、年払いによる解約抑制の効果

**成果物**
- 月別の「記録が発生する量」の見込みカーブ
- **12月時点で必要な累積獲得件数**（解約を織り込むと307件では足りない。何件獲れば307件が残るか）
- 年払い（980×12=11,760円 → 割引して9,800円等）を用意すべきかの判断材料。**年払いは解約を止め、かつ12月時点のMRR換算を早く積める**

**担当の適性** データ分析寄り。自社データ集計は開発側で
**期限** 着手から**10日**

### WP8 リリース直後のストア評価をどう作るか

**問い**

## 5. 品質基準（過去の調査から学んだこと）

`dl-target-20k-2026-09.md` は **原文到達ゼロ**のまま結論まで書いており、冒頭に自ら「数字を意思決定に使う前に原文確認をすること」と注記している。同じことを繰り返さないための基準:

1. **原文URLのない数字は、意思決定に使わない。** 報告書では「原文確認済み」「要約経由」を行ごとに区別する
2. **母数の定義が確認できない比率は使わない。**（「4軒に1軒」が母数によって3.4%〜32%に割れた例）
3. **単位を混ぜない。** DL / 登録者 / 利用組織 / アクティブ は別の数。競合の公表値はどれで語られているかを明記する
4. **反証を1つ探す。** 結論に都合の悪い事例を探してから書く

## 7. この計画の前提に対するプレモータム（12月末に失敗していたとしたら）

1. **調査だけして77日が終わった。** → Week 1 の3本で必ず分岐を確定させ、Week 2 から実行を始める。調査は実行を止める理由にしない
2. **団体一括が年度予算に阻まれ、12月に何も立たなかった。** → WP1 の判定1で早期に分かる。その時点で分岐C②（契約内定を成果に置く）へ切り替える。**12月に切り替えると言い訳になるが、10月に切り替えれば計画になる**
3. **無料枠を絞りすぎて誰も定着せず、有料以前に使われなかった。** → 段階1（入力データ蓄積）が最優先という順序（`product-context.md`）と衝突する。WP4 で競合の無料上限を確定し、**その上に線を引く。下には引かない**
4. **課金が10月中旬に載らず、実質1.5か月になった。** → WP6 を Week 1 に置いた理由。最短の課金開始日を先に確定する
5. **307件を集めたが、12月に解約が始まって30万円に届かなかった。** → WP7。累積獲得目標は307件より大きく置く
