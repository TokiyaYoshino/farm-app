# ADR: 0.1.0 の自己登録・課金・アカウント削除の作り方

- 日付: 2026-10-03
- 状態: **提案**（末尾「オーナーが決めること」の回答待ち）
- 関連: `20261001-account-model-self-signup.md`（何を作るか）、`20261001-pricing-freemium.md`（料金）、`docs/multitenancy-progress.md`（組織分離・ログインの穴）

## 背景
0.1.0 に「誰でも登録すると自分の農場ができる」「月980円・農場ごとの定期購読」「アプリ内アカウント削除（5.1.1(v)）」を入れると決めた（2026-10-01・2026-10-03）。
3つとも未実装。DB・認証・課金の土台に関わり後から覆しにくいので、実装前に作り方を決める。

## 決定（推奨）

### 1. 購入の検証は RevenueCat（`react-native-purchases`）に任せる
| 選択肢 | 長所 | 短所 |
|---|---|---|
| **RevenueCat（採用）** | レシート検証・更新・解約・返金の追跡を任せられる。Expo 公式の推奨2つのうちの1つ。月の売上（手数料を引く前）$2,500 まで無料 | 外部サービスへの依存。$2,500 を超えると月 $120（〜$10,000）→ 以降は売上の1% |
| expo-iap ＋自前検証 | 外部依存なし・費用ゼロ | App Store Server API の署名検証、更新・解約・返金の通知（Server Notifications V2）の処理を自分で作り、保守する。個人開発には重い |

- 理由: 課金の不具合は「払ったのに使えない」「払っていないのに使える」に直結し、信頼と売上を同時に失う。0.1.0 は**正しさと実装の速さ**を優先する
- 無料の上限 $2,500 ≒ 有料 約380農場（980円＝約$6.5で換算）。1年後の目標（約360農場）とほぼ同じ所で有料になる
- **再検討のトリガー**: 有料が300農場を超えたら、自前検証への移行と費用（月 $120 ≒ 売上の5%）を比べ直す

### 2. 購読は「農場（organization）」に付ける
- RevenueCat の利用者IDに **organization_id** を使う（人ではなく農場で1つ）。買えるのは**管理者だけ**。買えば農場の全員に効く（料金の決定どおり）
- 状態は新しいテーブル `organization_subscriptions` に置く（`organization_id` 主キー・`plan`（free/paid）・`status`・`expires_at`・`store`・`original_transaction_id`・`updated_at`）
  - 書くのは**サーバーだけ**: RevenueCat の Webhook を受ける `api/revenuecat-webhook.ts`（service role・署名の検証付き）
  - クライアントは読むだけ（RLS: `organization_id = jwt_organization_id()` の SELECT のみ）。**クライアントの申告で有料扱いにしない**
  - `organizations` に列を足さないのは、課金の書き込み経路を組織の表から切り離すため（Webhook の不具合が組織の行を壊さない）

### 3. Web 版では買わせない（状態の表示と効き目だけ）
- Web に購入の入口は作らない（Stripe 等は入れない）。アプリで買った有料は、農場単位なので **Web から使っても効く**（ガイドライン 3.1.3(b) の「他の場所でも使える」に当たる。アプリ内でも買えることが条件で、それは満たす）
- Web の管理画面には「有料（アプリで購読中）」の表示だけ置く

### 4. 自己登録はメール＋パスワード、組織作りはサーバー
- 登録はアプリから Supabase Auth の `signUp`（**本物のメール・確認メールあり**）。確認後の初回ログインで `api/create-organization.ts`（service role）を呼び、`organizations` の行と本人の `users` 行（role=admin）を作る。**2回呼んでも1つしかできない**（既に users 行があれば何もしない）
- 組織の作成権限はクライアントに渡さない（`20261001-account-model-self-signup.md` の方針）
- 確認メールの送信に**独自の SMTP が要る**（Supabase 標準の送信は1時間数通の制限があり、公開には使えない）。送信元は `info@kishufarm.com` のドメイン
- ログイン画面は「メールアドレス**または**ユーザーID」を受ける（既存の作業者はユーザーIDのまま）。ユーザーIDからメールを引くのは、今の「全員分を匿名で読める」形をやめて**1件だけ返す RPC** に置き換える（`multitenancy-progress.md` の漏れ。自己登録で本物のメールを入れる前に必須）
- Google 等の外部ログインは入れない（入れると Sign in with Apple も必須になる・ガイドライン 4.8）

### 5. アカウント削除は「誰が消すか」で3通り
| 消す人 | 起きること |
|---|---|
| 作業者、または他にも管理者がいる管理者 | 本人のログイン（Auth ユーザー）と通知の端末トークンを消す。`users` 行は**氏名を残したまま**ログインできない状態にする（**農場の記録＝農薬の使用記録の記入者を壊さない**。2026-10-03 オーナー決定。プライバシーポリシーに「削除後も農場の記録に付いた氏名は農場の記録として残る」と明記する） |
| 農場に1人だけの人（個人の利用者） | 農場ごと全部消す（記録・写真を含む）。確認を2段階にする |
| 他に利用者がいる農場の唯一の管理者 | 「他の人を管理者にしてから消す」か「農場ごと消す（全員のアカウントも消える）」を選ばせる |
- 処理は `api/delete-account.ts`（service role）。削除画面で**購読は自動では止まらない**こと（App Store の設定で解約が必要）を伝え、解約画面へのリンクを置く
- 写真（Storage `report-images`）も消す対象に入れる

### 6. 回数の数え方は `api/_auth.ts` で農場ごとに
- 今の `checkDailyLimit`（人ごと・1日・暴走止め）を、`checkOrgQuota(organizationId, kind)` に置き換える。数える先は `ai_outputs` を `organization_id` で
- 枠は料金の決定どおり（無料: 相談 週3件・写真 週1回／有料: 相談 1日8件・写真 1日3回）。**週は日本時間の月曜0時で切る**（「毎週月曜に戻る」と説明できる）
- 「記録に聞く」（`api/search-chat.ts`）は今 `ai_outputs` に残していない。料金で相談に含めると決めたので、**残すようにして数に入れる**
- 数えられなかったときは今どおり通す（fail-open）。ただし記録する

## 影響
- DB: `organization_subscriptions` 新設（RLS 必須）。`users` 行の匿名化に備え、記録の記入者表示が null・置き換え名で壊れないか確認
- API: `create-organization` / `delete-account` / `revenuecat-webhook` 新設、`_auth.ts` の回数制限を置き換え、`search-chat` に保存を追加。**契約テストを先に書く**（`scripts/test-*.mjs`）
- アプリ: 登録画面・購読画面（3.1.2 の表示: 期間・価格・自動更新・解約方法・規約とプライバシーへのリンク）・削除画面・上限到達の表示
- 文書: `public/privacy.html`（「運営者が発行したアカウントに限る」の記述・委託先に RevenueCat・アカウント削除の手順）、利用規約（定期購読の条項）、App Store の「App のプライバシー」に購入履歴を追加
- ロックイン: RevenueCat。利用者IDに organization_id を使うので、移行時も農場との対応は保てる

## 実装状況（2026-10-04）
| 項目 | 状態 |
|---|---|
| 6. 農場ごとの回数の枠 | `api/_quota.ts`＋契約テスト `scripts/test-org-quota.mjs`（39件）。日報・次の散布時期・音声の整理も枠に入れた（2026-10-04 オーナー決定「従量課金がかかるものは無制限にしない。1日1回くらい」）。無料: 日報 1日1回・次の散布時期 1日1回・**音声の整理 1日5回（提案値）**。音声は記録の入口で、1回だと2件目の記録から声で入れられなくなるため。有料の3つの数字（3/3/30）も提案値。**どのエンドポイントにもまだつないでいない**（購読の表が無いうちにつなぐと全農場が無料扱いになり、既存の農場が週3件に絞られる）。つなぐのは購読の表と同時 |
| 5. アカウント削除 | `api/delete-account.ts`＋契約テスト `scripts/test-delete-account.mjs`（33件）。**消した内容は控えの表 `deleted_data_archive` に30日残す**（2026-10-04 オーナー決定。「間違えて消した」に手で戻せるように）。ログインはすぐ消し、写真は30日後に `api/purge-deleted.ts`（Vercel Cron・毎日 3:00 JST・契約テスト13件）が控えと一緒に消す。DB の SQL `scripts/migrations/2026-10-04-delete-organization-data.sql` は**本番未適用**（オーナー承認待ち）。Vercel に `CRON_SECRET` の登録が要る（未登録の間、完全削除は動かないだけで害は無い）。privacy.html に「削除後30日で完全に消去」の追記が要る。アプリの削除画面は未着手 |
| 4. 自己登録 | 未着手（確認メールの送信サービスの決定待ち） |
| 1〜3. 課金 | 未着手（RevenueCat の採否待ち） |

**未決（オーナー）**: 日報・次の散布時期・音声の整理（`daily_report` / `pest_advice` / `voice_structure`）は、料金の決定で無料・有料のどちらの差も書かれていない。今は回数の枠の対象外（暴走止めの「1人1日50回」だけ）にしてある。無料でも無制限でよいか。

## オーナーが決めること
1. **RevenueCat を使ってよいか**（推奨: 使う）— 2026-10-03 オーナーが料金条件を確認中。無料の上限は手数料前の売上で数え、料金体系は先方が変えうる
2. **確認メールの送信サービス**（推奨: Resend 等の無料枠＋ `kishufarm.com` のドメイン認証。DNS の設定作業が要る）— 2026-10-03 オーナー検討中
3. ~~作業者が消えたとき、記録の記入者名を残すか~~ → **氏名を残す**（2026-10-03 決定。5節に反映）
4. **1人農場の削除で、記録を書き出してから消す導線を付けるか**（推奨: 0.1.0 では付けない。削除の確認画面で「記録は戻せない」と明示）
