# 公開向けの説明面（/about）を1枚作る

- 日付: 2026-09-20
- 状態: 採用
- 種別: 新機能（プロダクト外面）＋リリース判断
- 関連: `docs/research/dl-target-20k-2026-09.md`（獲得経路が律速）、
  `docs/research/competitor-app-reviews-2026-08.md`（5★を分けるのは記録の出口）、
  `docs/app-store-submission.md` 6章、`docs/decisions/20260912-release-line.md`（3問の判定）

## 課題（Why）

`dl-target-20k-2026-09.md` の結論は「**律速はアプリの中ではなく外の獲得経路**」。
伸びた事例4件（アグリハブ／KSAS／アグリノート／レイミー）が4件とも既存チャネル
（JA・農機メーカー・農薬メーカー）への接続を成長の説明変数にしており、UI改善を挙げた
事例はゼロだった。

ところが**そのチャネルに見せる面が存在しない**。実測（2026-09-20）:

| # | 事実 |
|---|---|
| 1 | `kishu-farm.vercel.app` はルートが即ログイン画面（`src/App.tsx:2931`）。提携先・記者・農家が開いても、何のアプリか分からない |
| 2 | 公開されている静的ページは `public/privacy.html` の1枚だけ。**問い合わせ先を書いた面が無い** |
| 3 | App Store Connect は**サポートURLが必須項目**。privacy だけでは埋まらない |
| 4 | `index.html` の `og:description` は「農場の作業記録・予定・分析をまとめる農作業レポートアプリ」の1行で、`og:image` は無い |

つまりこの1枚は、**マーケ（提携打診の入口）と申請（サポートURL）の両方**を同時に埋める。
調査が名指しした「外の獲得経路」に手を付けるとき、最初に必要になるのはこれ。

## 決めたこと

### 紹介とサポートを1枚に統合する（`/about`）

分けない。この規模で2枚に割ると、運営者情報（未記入のTODO）が2箇所に散る。
`public/about.html` の1枚に「何ができるか」と「お問い合わせ」を同居させ、
App Store Connect の**サポートURLとマーケティングURLの両方に同じURLを出す**。

### ルート（`/`）は触らない

`/` をLPにして「ログイン」ボタンからアプリへ、という案は採らない。`src/App.tsx` は
ルーターを持たない（CLAUDE.md の構成）ため、ルートの出し分けはSPA側の大工事になる。
既存利用者が毎日開く面でもあり、摩擦を増やす。
`public/privacy.html` と同じ形——**静的HTML＋`vercel.json` の rewrite**——で足りる。

ログイン画面の下に「このアプリについて」の補助リンクを1本だけ足す。
worker にURLを渡したとき、ログイン画面しか見えないと何のアプリか分からないため。

### 訴求の中心は「記録の出口」に置く

`competitor-app-reviews-2026-08.md` の結論3が「**5★を分けるのは記録の出口があるか**」
（振り返り・年次比較・売上・農薬使用回数）で、高評価は例外なく見返りに言及していた。
逆に同調査は**高齢者への言及が89件中0件**で、「簡単な画面」を求める外部証拠は無いとしている。

よって LP の見出しは「かんたん」「やさしい」ではなく、**記録した後に何が返ってくるか**で書く。

### 料金は書かない

料金プランは `20260823-pricing-plan-review.md` で「要再検討（課金軸を機能から蓄積データの
活用範囲へ移すか）」の状態。**外に出した数字は引っ込められない**ので、価格は載せず
「招待制」とだけ書く。決まってから足す。

### 調査の数値は引用しない

`dl-target-20k-2026-09.md` は自分で「**原文に到達できたページがゼロ・検索要約経由**」と
明記している。打ち手の方向（チャネル律速）は4件一致で頑健だが、**個々の数値を対外資料に
載せない**。LP に市場規模・競合比較の数字は一切書かない。

### 今回やらないと明言するもの（Won't this time）

- **`og:image`（OGP画像）** — 1200×630 の PNG が要るが、この repo に画像生成の依存が無い
  （`playwright` 等の devDependency 追加は、この1枚のためには重い）。
  **ストア掲載情報の回（スクリーンショット5枚を撮る作業）と同時に作る**のが筋なので、そこへ送る。
  壊れた `og:image` を今置く方が害が大きいため、タグ自体を足さない
- **アプリの実画面スクリーンショット** — 同上。デモモード（`npm run demo`）で撮れるが、
  App Store 用の撮影と一緒にやる
- **運営者の正式名称・連絡先メール** — オーナーの手番。`privacy.html` と同じ形式で
  TODO コメントを置く。**申請前に2箇所（privacy / about）をまとめて埋める**
- 英語版・SEO 構造化データ・問い合わせフォーム

## 検討した代替案

- **案B: `/` をLPにして `/app` にログインを移す** → ルーターが無く、SPA の大工事になる。
  既存利用者の導線も変わる。**見送り**
- **案C: LP とサポートページを分ける（`/about` と `/support`）** → 運営者情報のTODOが
  2箇所に散り、いま埋める中身の量に対して面が多すぎる。**見送り**（利用者が増えて
  問い合わせの型ができたら分ける）
- **現状維持（作らない）** → 調査が律速と名指しした獲得経路に着手できず、
  App Store Connect のサポートURLも埋まらない。**見送り**

## 影響範囲

- DB / RLS: **なし**（静的HTML1枚と rewrite 1行）
- 既存機能: 削除なし。ログイン画面に補助リンクを1本追加するのみ
- AppStore: サポートURL／マーケティングURLの提出先ができる。
  「一般ユーザーが自由登録できない理由」（ガイドライン 5.1.1(v)）を LP 本文でも説明し、
  審査備考と食い違わないようにする
- 法規・農業実務: 相談・診断の回答が参考情報であることを LP にも明示する
  （CLAUDE.md「農薬・診断の注意書きでは AI であることを明示する」）。
  農薬の使用回数については画面と同じく「超過の疑いのみ警告し、あと何回使えるとは言わない」
  という非対称の仕様（`20260805-pesticide-precheck.md`）と矛盾する書き方をしない

## プレモータム（半年後に失敗していたとしたら）

1. **LPを作ったが、誰も見に来ない。** → LP 単体では流入は増えない（調査が
   「ストアページに来る人数にUXは効かない」と書いたのと同じ構造）。これは**チャネル打診の
   前提**であって施策ではない。次の一手（接触先リストと打診文面）に進むこと
2. **運営者情報のTODOが埋まらないまま公開され、問い合わせ先の無いページが晒される。**
   → 申請前チェックに privacy と about の2点セットで入れる（本ログに明記）
3. **料金を書かなかったため、提携先から「いくらなのか」と最初に聞かれる。**
   → それでよい。聞かれてから答える方が、外に出した数字を後から変えるより安い
