# 相談の返答を、文数の縛りではなく「コードが数えた事実」で決める

- 日付: 2026-09-06
- 状態: 採用
- 種別: 仕様変更（AI出力・プロンプト）

## 課題（Why）

「相談の動作を、他のAIエージェントや普段使いのAI（ChatGPT など）と同じ感じに寄せてほしい」という相談から。

`api/advise.ts` は返答を **「2〜3文」「全体で500字程度」** と固定で縛っていた。これは `docs/decisions/20260829-ai-output-structure.md` の実測（本文74字に対して注釈179字＝注釈が本文の2.4倍）への対応として入れたものだが、**縛ったのは注釈ではなく本文の方だった**。結果として次が起きる。

- 「今週は雨が続くけどどうする？」のように一言で済む質問にも、律儀に3文書く
- 「摘果のやり方を教えて」のように手順を聞かれても、3文で打ち切る
- 情報が足りなくても聞き返さず、推測で埋めるか「判断できない」で終わる

普段使いのAIとの体感差は、モデルの賢さより**この事務的な打ち切り方**にある。なお同ADR自身が「一律に字数上限を下げる」案を実測で否定し、**問題は総量ではなく配分**だと結論している。本件はその結論を本文側にも適用するもので、方針転換ではなく適用漏れの回収にあたる。

## 決めたこと

プロンプトのみを変更する（スキーマ・保存・画面はそのまま）。

| | 変更前 | 変更後 |
|---|---|---|
| 返答の長さ | 「2〜3文」 | 「長さは質問に合わせる —— 一言で済むことは一言で、手順や選び方を聞かれたら必要なだけ書く」 |
| 全体の字数 | 「全体で500字程度に収める」 | 上限を置かない。代わりに **actions / watch_points と同じ内容を reply で書き直さない** ことを禁じる |
| 情報不足のとき | 指示なし（推測か「判断できない」） | **`follow_up_question` をスキーマに追加**（40字以内の疑問文 or null）。reply は分かる範囲で完結させ、聞き返しはこの枠に置く |
| `max_tokens` | 1200 | 1800 |

### 注意書きは「毎回」から「初出だけ＋常設1行」へ

`20260829-ai-output-structure.md` で注意書きは折りたたみ（`この回答の前提`）に入れたが、**文言自体は毎ターン同じものが再び入る**ため、会話が伸びるほど同じ文が積み上がる。畳んであっても件数バッジは毎回付き、開けば同じ文が並ぶ。

- 同じスレッドで既に出た `limits` / `sources` は、2回目以降の回答では出さない（`unknowns` はその回固有の内容なので対象外）
- ただし**農薬のラベル確認だけは常に見える場所に置く**。重複を省くと初回の1件が画面外に流れるが、農薬使用基準の遵守は法的義務（罰則あり・`agriculture` スキル `references/legal.md`）なので、畳んだ中の1回では足りない。入力欄の上に常設の一行として出す

**消すのではなく分ける**（同ADRの原則）は維持している。保存されている `limits` は変えておらず、監査ログとしては全回分そのまま残る。

### 聞き返しはプロンプトではなくスキーマで解いた

最初はプロンプトの指示（「聞き返してよい」→「reply の最後に1つだけ質問を置く」）で実現しようとしたが、**実測で2回とも一度も聞き返さなかった**。理由は測って分かった —— 聞くべきこと（「具体的な病害虫の情報が不足」）を `unknowns` に流していた。`unknowns` という置き場がスキーマにある以上、モデルはそちらへ行く。

そこで `follow_up_question` を専用の枠として足し、役割を明示的に分けた。

| 枠 | 意味 | 画面 |
|---|---|---|
| `unknowns` | 渡された情報では**判断できないこと**（限界） | 前提として折りたたむ |
| `follow_up_question` | **利用者に尋ねること**（1つだけ・40字以内・無ければ null） | 返答の最後の段落として本文と同じ吹き出しに出す |

`work_type` を語彙の完全一致だけ通し、`due_from`/`due_to` を日付の形だけ通しているのと同じ扱い —— **スキーマが守るのは形、コードが守るのは意味**（`20260829-ai-output-structure.md`）。サーバー側では空文字と文字列 `"null"` を null に倒し、120字で切る。

聞き返しは別列を作らず、保存時に `content` の最後の段落として本文に連結する。利用者にとっては返答の一部（会話）であり、分けても表示上の利点が無く、マイグレーションが1本増えるだけのため。

**結論を先に述べる原則（`1文目で結論`）は維持する。** これは `20260829-ai-output-structure.md` の中核で、長さの話とは別物。

### 聞き返しを「1つだけ・答えたあと」に限定した理由

聞き返しは普段使いのAIらしさの中心だが、無制限に許すと質問返しで会話が進まなくなる。屋外・手袋・繁忙期という利用環境（`docs/spec-ai-features.md` 3.1）では往復そのものがコストなので、**答えを出さずに聞くだけの返答を禁じる**形にした。

### `max_tokens` を上げた理由

返答が伸びると、`response_format: json_schema`（strict）の JSON が途中で切れる。切れると JSON 全体がパースできず 502（「助言結果を読み取れませんでした」）になり、**返答が長いときだけ失敗する**という分かりにくい壊れ方をする。1200 は本文90字前提の値なので余白を持たせた。

## 検討した代替案

- **案B: 字数上限を 500 → 1000 字に緩めるだけ** → 却下。数字を変えても「質問に関係なく一定量を書く」構造は変わらない。一言で済む質問に長文が返る方向にも振れる
- **案C: モデルを上げる（gpt-4o-mini → gpt-4o）** → **実測して却下**。同じ質問・同じ材料で比較したが、gpt-4o-mini との差は「9月9日頃」対「9月10日以降」程度で、**コストに見合う差は確認できなかった**（入力 $0.15→$2.50/1M・出力 $0.60→$10/1M と十数倍）。materials を渡した gpt-4o-mini が自農場の記録にある「べと病」を挙げるところまで到達しているのに対し、モデルを上げても新しく分かることは増えない。**効くのはモデルではなく材料**という結論は両モデルで一致した
- **案E: 記録が薄い作付けに、農場のほかの作付けの記録を参考として渡す** → **実装して実測した結果、効果を確認できず取り下げ**。本番はキャベツ0件・たまねぎ3件と作付けごとの記録数の偏りが大きく（35件中の内訳）、薄い作付けでは一般論しか返らないため試した。たまねぎ3件＋ほかの作付け7件で比較したが、「水やり＋病害虫チェック（定植7日目の根付き確認）」→「除草」と変わっただけで、良くなったとは言えない。ほかの作付けの作業を引きずるだけの疑いがあり、誤帰属のリスクと入力トークンだけが増えるため、変更を戻した
- **案D: 返答を自由文に戻す（構造化出力をやめる）** → 却下。`20260829-ai-output-structure.md` が実測に基づいて構造化した判断を覆すことになる。今回必要なのは形式の自由度ではなく長さの自由度
- **現状維持** → 却下。差別化の中核である相談機能が、汎用AIと比べて明確に不自由に見える

## 影響範囲

- **DB / 権限**: なし
- **既存機能**: `api/advise.ts` のプロンプトと `max_tokens` のみ。スキーマ・保存形式・画面（折りたたみ表示）は未変更。作物ごとの相談・畑全体の相談の両方に効く
- **コスト**: 出力トークンが増える（gpt-4o-mini: output $0.60/1M）。本文90字→300字で1回あたり +$0.0001 程度と小さいが、~~**Free 日次上限は設計のみで未実装**（`docs/roadmap.md`）なので、利用が伸びるほど素通しで効く~~ **訂正（2026-09-17）: 実装済み。** 2026-09-10 の Web版リリースで `api/_auth.ts` の `checkDailyLimit` が入っている（画像診断20回/日・その他50回/日・fail-open）
- **ストア審査 / 規制・業界固有の実務**: なし。農薬の数値を LLM に生成させない・渡された登録情報の範囲外を述べさせない・製品ラベル確認を促す、の3点はすべて維持（契約テストで担保）

## プレモータム（半年後に失敗していたとしたら、何が起きたか）

1. **長さの自由度を与えた結果、毎回長文が返るようになった。** 「質問に合わせる」は LLM の裁量なので、実際には常に長い方に倒れる可能性がある。→ 実利用の返答を見て、長さの分布が質問に相関していなければ「短い質問には短く」の例示をプロンプトに足す
2. **聞き返しが増え、答えにたどり着くまでの往復が伸びた。** 「1つだけ・答えたあと」と縛ってはいるが、守られる保証はプロンプトのみ
3. **返答が伸びたぶん、注釈（limits）が相対的に埋もれた。** 本文が長くなると、折りたたまれた前提はますます開かれなくなる。農薬に関する免責が読まれないまま踏み込んだ質問をされるリスクは `20260906-general-advice-entry.md` のプレモータム1と同根

### 実測（本物の gpt-4o-mini・ほうれん草・記録3件・famic 未紐付け）

契約テストが見られるのは「プロンプトに指示が載っているか」までなので、`20260829-ai-output-structure.md` と同じく実際に OpenAI を叩いて測った（4問で $0.0014 ≒ ¥0.2）。

| 質問 | 変更前の想定 | 実測（変更後） |
|---|---|---|
| 「今日は雨だけど防除できる？」 | 2〜3文固定 | **70字 / 2文**・聞き返しなし |
| 「間引きのやり方を教えて」 | 2〜3文で打ち切り | **83字 / 3文**（本葉2〜3枚・株間10〜15cmまで入る） |
| 「葉の様子がおかしい」 | 推測で答えて終わり | 72字＋**聞き返し「葉の異常はどのような症状ですか？」** |
| 「アブラムシに効く薬を教えて」（畑全体） | — | 薬剤名を出さず作物選択へ誘導＋**聞き返し「対象の作物は何ですか？」**。`limits` に作物未指定の旨、`registrationFacts` 0件 |

長さが質問に応じて変わること、聞き返しが必要な場面だけで出ること、畑全体での安全側の縮退が実際に効くことを確認した。

### 返答の中身は「LLMを賢くする」では動かない（同一質問での比較）

「返答が一般論すぎる」という指摘から、材料とモデルのどちらが効くかを切り分けた（3問×3条件、計$0.004）。結論を先に書くと、**LLM の知識そのものを厚くする手は無い**。動くのは、コードが用意した事実を渡したときだけ。`20260829-ai-output-structure.md` の「数えるのはコード、言い換えるのが LLM」がそのまま当てはまる。

| 条件 | 「今週、防除はいつやるのがいい？」 |
|---|---|
| A 現状（材料なし） | 「今週中に防除を」（一般論・日付なし） |
| B 4o-mini＋実天気＋記録10件 | **「9月9日頃」**と日付を出し、「9月の作業は？」には自農場の記録にある**べと病**を挙げた |
| C gpt-4o＋同じ材料 | 「9月10日以降」。**B との差はほぼ無い**のにコストは十数倍（上記・案C） |

**モデルを上げても変わらず、事実を渡したときだけ変わる。** B が出した「9月9日頃」も「べと病」も、LLM が考えたのではなく渡した材料の言い換えでしかない。これは `docs/roadmap.md` の戦略順序（入力データ蓄積 → 価値化）と、`20260823-pest-advice-history.md` の「唯一の差別化は記録とAIが同じ場所にあること」を実測で裏づけている。

### 相談にも集計を渡す（本命・同日に実施）

この観点で調べると、**相談だけが「コードが計算した事実」を受け取っていなかった**。

| 機能 | 受け取っている事実 |
|---|---|
| 防除助言 | `formatSprayHistoryForPrompt`（前回散布からの日数・直近の散布履歴・同一商品の繰り返し・昨年同時期） |
| 記録検索 | `formatWorkCountsForPrompt`（年×作業種別の件数）／`formatPesticideUsageForPrompt`（残り使用回数） |
| 相談（改修前） | `formatAdviceHistoryForPrompt` のみ（過去の助言と実施状況）。作業実績は生の記録行だけで、集計は LLM 任せ |

差別化の中核（`docs/spec-ai-features.md` 8章）がこの状態だったので、リクエストに `aggregates`（4000字以内）を足し、クライアントが `formatSprayHistoryForPrompt` と `formatWorkCountsForPrompt` の出力を渡すようにした。**新しい計算は一切書いていない**——画面（ホームの「今日の一手」）・防除助言と同じ関数を通すので、AI の言うことと画面の数字が食い違わない。プロンプトでは「## 自農場の集計（コードが数えた確定値・数え直さないこと）」として別ブロックに置く。

実測で分かったのは、**渡すだけでは使わない**ということ。前回の散布9日前・同一商品3回連用を渡しても、最初の版は一般論のままだった。「散布の時期・間隔・回数の質問では集計を必ず答えに反映すること」を明示して初めて使うようになった。

| 質問 | 集計なし | 集計あり（指示つき） |
|---|---|---|
| そろそろ防除したほうがいい？ | 「防除は必要です。たまねぎは病害虫の影響を受けやすく…」 | 「次回の防除を検討する時期です。**前回の散布から9日経過**しており…」 |
| 今年はどんな作業をしてきた？ | 日付を列挙するだけ | 「**防除3回（7/30・8/14・8/28）、施肥1回、除草1回**」と集計どおり |

もう一つ、実測で危ない読み替えが見つかった。同じ商品を3回使っている事実を、モデルが**「だから次も散布を」の根拠にした**。連用は薬剤耐性の観点で注意する材料であって推奨の根拠ではないので、「同じ薬剤を続けてよい根拠にしないこと」を明示した（有効成分・系統のデータが無く同一系統の判定はしない、という `20260823-pest-advice-history.md` の立場は維持）。

本番データの実態（2026-09-06 時点）: 記録35件は**全件が作付けに紐づいている**が、作付けごとの偏りが大きい（ほうれん草19 / にんにく9 / ぶどう4 / たまねぎ3 / キャベツ0）。`crops.famic_crop_name` は7件中3件のみ紐付け済みで、残り4件の作付けでは `registrationFacts` が常に空になる。**相談の中身を厚くする一番の手は、機能の追加ではなく記録の蓄積と作物名の紐付け**という結論になる。
