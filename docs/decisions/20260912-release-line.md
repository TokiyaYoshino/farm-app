# App Store リリースの線を「完成度」から「判定できる状態」へ移す

- 日付: 2026-09-12
- 状態: 採用
- 種別: リリース計画＋スコープ管理
- 関連: `20260909-advice-tab-keep-with-exit-criteria.md`（撤退条件）、`20260909-web-release-and-rollback.md`（Web版リリース）、`docs/handoff-ai-entry-ux.md`（凍結する論点）

## 課題（Why）

「最終調整がずっと続いてリリースが後ろ倒しになる。どこまでやるか」という相談。
調べると、止まっているのは作業量ではなく**リリースの判定条件が「機能の完成度」に
置かれていて、終わりの条件が存在しないこと**だった。

実測（2026-09-12）:

| # | 事実 |
|---|---|
| 1 | Web版は 2026-09-10 に既にリリース済み。後ろ倒しになっているのは App Store 版 |
| 2 | **App Store に必要な機能開発はゼロ。** 残りは Apple Developer 登録・privacy の連絡先・本番APIキー確認で、いずれもオーナーの手番 |
| 3 | AIの情報設計を3回作り直し（08-23 / 09-06 / 09-09）、**3回とも「効果は未検証」**で終わっている |
| 4 | 本番の worker は0人・記録18件（4.5か月）・AI呼び出しは開発時の確認のみ。**配置の良し悪しを判定する材料が存在しない** |
| 5 | `20260909-advice-tab-keep-with-exit-criteria.md` のプレモータム1が既に「**使う人を増やすことが、どのUI改善よりも先**」と名指ししている。`handoff-input-redesign.md`（08-09）も同じことを書いていて、1か月以上未実行 |

**結論: 最終調整が終わらないのではなく、「出さないと分からないこと」に投資し続けている。**
撤退条件と `entry_point` 計測は 09-09 に実装済み＝**測る仕掛けはもう完成していて、
足りないのはデータだけ**。データは worker が使い始めない限り増えない。

## 決めたこと

### リリース判定を3つの事実だけにする

App Store 0.1.0 を出す条件は次の3つ。**これ以外は出してから直す。**

1. `advice_threads` の RLS が組織スコープになっている
2. Apple Developer 登録 / privacy の運営者情報 / 本番 `OPENAI_API_KEY` が済んでいる
3. worker アカウントが1つ以上あり、admin 以外の入力が1件以上ある

3 を入れたのは、**0.1.0 の目的が「審査を通すこと」であり、機能の完成度ではない**から。
そして worker が居ないまま出すと、次の判断材料もまた1か月得られない。

### 今回やらないと明言するもの（Won't this time）

- `docs/handoff-ai-entry-ux.md` の 4-1〜4-7（配置の詰め）
  → **凍結解除は `ai_outputs.entry_point` が n≧30 に達した時点。** それまでに触っても
  4回目の「効果は未検証」になるだけで、3回分と同じ結果になる
- 越境アクセスの実地テスト（2組織目）→ **他農場へ配る前**の必須項目であって、
  App Store 単独公開の前提ではない（審査に出るのは霧珠ファームの1組織）
- App.tsx の分割、lint 負債

## 配置・デザインを「どこまでやったら申請するか」（2026-09-13 追記）

上の3条件はインフラ側のゲートで、**「機能の配置・デザインをどこまで詰めるか」には答えていなかった**。
これがオーナーの実際の問い。**新しい基準は作らない。既にリポジトリに2つ書いてある。**

| | 出典 | 中身 |
|---|---|---|
| 審査ゲート | `docs/app-store-submission.md` 7章 | Apple が実際に落とす5項目（2.1 / 4.2 / 5.1.1 / 5.1.1(v) / 1.2）。**配置の洗練度は審査対象ではない** |
| 定着ゲート | `docs/decisions/20260824-no-manual-test.md` | 必達3タスク（畑を1つ登録 / 作業を1件記録 / 農薬を撒いたことを記録）が説明ゼロで完了すること |

この2つ以外に、配置・デザインの門番は置かない。

### 迷ったときの判定（3問）

> 1. 直さないと**審査で落ちる**か
> 2. 直さないと**必達3タスクが説明ゼロで完了しない**か
> 3. 直さないと**法令記録が欠ける／画面とAIの数字が食い違う**か

**どれでもなければ出してから。** decisions に1行残して次へ。「良くできる」は全部この枠に入る。

### 必達3タスクは、1人では実行できない（2026-09-13 実測・ADRの補正）

`20260824-no-manual-test.md` の必達3タスクは「農家1人に全部やってもらう」前提で書かれているが、
**実装では ① が worker ロールで実行できない**。`src/App.tsx` の管理タブは
作物・圃場・農薬の「追加」をすべて `isAdmin` で囲っている（3731 / 3889 / 3961 行）。

実運用でも圃場を登録するのは管理者なので、**タスクを役割で割る**のが正しい。

| # | タスク | 誰が | 備考 |
|---|---|---|---|
| ① | 畑を1つ登録する | **管理者** | worker には権限が無い。毎日の導線でもない |
| ② | 今日やった作業を1件記録する | **worker** | ここが本丸 |
| ③ | 農薬を撒いたことを記録する | **worker** | 事前に農薬マスタに1件以上必要（追加は管理者のみ） |

管理者側の事前準備（作物・圃場・農薬が1件以上ある）が済んだ状態から worker に渡す。
**準備の手間そのものも観察対象**——`handoff-input-redesign.md` 2.5 が
「核心の質問は『作業者アカウントを作ろうとしたことはあるか。どこで止まったか』」と
書いているとおり、入力UIより前に配布の段階で止まっている可能性がある。

### 定着ゲートは「合格」ではなく「実施」

`20260824-no-manual-test.md` は「これは門番ではない」と明記している。それと矛盾させないため、
**ゲートは"必達3タスクのテストを1回やったこと"であり、"出た詰まりを全部直したこと"ではない**。
出た詰まりのうち上の3問に当たるものだけ直し、残りは既知課題として記録して出す。

### この基準に当てた結果（2026-09-13 実測）

`docs/handoff-ai-entry-ux.md` の未決論点7件のうち、**申請前に直すべきものはゼロ**。
4-2 / 4-3 は 09-12 のマージで解消済み、4-1 / 4-4 / 4-5 は Web 専用で申請物に無い、
4-6 は必達4（＝「記録して次で直す」枠）、4-7 は下記の順序で意図的に許容する。

デザイン側も測った。実質的なトークン違反は **1件**（`src/components/GanttChart.tsx:16` の
`#4CAF50` がトークン外の緑）。他は正当な例外（起動失敗時のエラー画面・グラフの系列色・
帳票の印刷CSS）で、角丸の直値173件のうち65件は `999`＝ピルそのもの。いずれも3問に当たらない
ので、機能追加のついでに返す（`technical-decisions.md` の方針）。

## 開発順序: Web で調整し、固まったら Expo に反映する（2026-09-13 決定）

Web と Expo は同じ Supabase・同じ `api/*` を見ていて、画面もほぼ対応する。
**Web は デプロイが git push だけ・デモモードで認証なしに確認できる**のに対し、
Expo は EAS ビルドと審査が挟まる。よって**調整は Web で行い、効いたものだけ Expo に移す**。

**ただし申請を待たない。** 「Web が固まってから Expo に反映して申請」は、まさに今回
診断した後ろ倒しの構造そのもの。**申請は今の Expo（09-06 ベース）で出し、Web の調整結果は
0.2.0 に載せる。** 0.1.0 の目的は審査を通すことであって、最新の配置を載せることではない。

### この順序で注意すること

- **スクリーンショットは Expo の実機／シミュレータで撮る。** Web と見た目が違うので、
  Web の画面を出すとガイドライン 2.3.3（metadata が実物と一致）に触れる
- ~~**`ai_outputs.entry_point` を Expo にも入れる（要対応）。**~~ **対応済み（2026-09-16）。**
  Web の `saveAiOutput` は `entryPoint` を必須にしていたが、Expo 版
  （`expo-prototype/lib/ai.ts`）は送っておらず、**撤退条件（n≧30）を判定するデータが
  アプリからは一切記録されない**状態だった（09-10 の「計測が静かに欠けていた」と同じ構造）。
  Web と同じく **必須の引数**にして、6つの呼び出しすべてに導線を通した。
  必須にしたのは Web と同じ理由で、任意だと導線を足したときに書き忘れ、
  「使われていない」と読めて集計が嘘になるため。**型が通ることが配線の証明**になっている
  （`npm run typecheck` が通る＝渡し忘れが無い）。割り当てはこう:

  | 画面 | シート | `entry_point` |
  |---|---|---|
  | ホーム | 次の散布時期／相談／写真診断 | `home` |
  | 記録一覧 | 日報／写真診断／相談 | `record_list` |
  | 記録詳細シート | 写真診断 | `report_detail` |
  | 相談タブ | 相談 | `thread` |
  | 相談タブ | 写真診断 | `thread_tool` |
  | 管理タブ 登録作物 | この作付けを相談する | `crop_row` |
  | ＋記録 | メモ欄のAI整理 | `note_field` |

  **`crop_row` は Web の型に無い値**。Web の管理タブに相当の入口が無いため増やした。
  `thread` に寄せる手もあったが、撤退条件は `thread` / `thread_tool` の**占める割合**で
  決まる（`20260909-advice-tab-keep-with-exit-criteria.md`）ので、相談タブを経由しない
  呼び出しをそこに混ぜると**相談タブが実際より使われているように見え、判定が甘くなる**。
  集計時は「相談タブ = `thread` + `thread_tool` のみ」で数えること
- Web 専用のまま残っているもの: 利用者の作成（`set-user-auth` 経由）、デモモード、
  相談タブ／スレッド、ホームの未実施バッジ。**利用者の作成が Web のみ**なのは、
  worker を配る導線が管理者の PC に限られるということ（`handoff-input-redesign.md` 2.5）

## 実測で判明した、既存ドキュメントとの食い違い（訂正）

**`20260909-web-release-and-rollback.md` の「RLS が `allow_all` のまま」は誤り。**
anon キーで本番を叩いた結果:

| テーブル | 結果 |
|---|---|
| `reports` / `crops` / `crop_advice_messages` | 0 件（実ポリシーが効いている） |
| `users` / `sessions` / `device_tokens` | 401（`users` は列 grant で `login_id`/`email` のみ） |
| **`advice_threads`** | **4 行そのまま返る** |
| **`work_categories`** | **6 行そのまま返る** |

RLS は 2026-09-05 に適用済みで、**残っていた穴は2表**だった。
`advice_threads` は `2026-09-09-release.sql` が `allow_all` で作っている（同 ADR が自分で
警告していた箇所）。`work_categories` は 09-05 の実施記録に「`to authenticated` 限定に修正」と
書いてあるのに実測では匿名から読める＝**記録と実態が食い違っている**。
`scripts/migrations/2026-09-12-rls-anon-leaks.sql` で両方を塞ぐ。

**ここから学んだこと**: 「ポリシーを作った」という記録は、実際に塞がっている証拠にならない。
**外から匿名で叩いて確かめる**のが唯一の確認方法（`pg_policies` の目視すら、09-05 に
`work_categories` を見落としている）。この検査は SQL 不要で、キーは既にバンドルに入っている。

**なぜ食い違ったか**: 09-05 の実施記録が作業ツリーに未コミットのまま残っており、
別セッションがそれを見られなかった。**実施記録は作業当日にコミットする。**

  09-09 の相談タブに機能が移ったことによる置き換えで、機能自体は相談タブに残っている
- 審査: 新規実装なし。~~デモアカウントは `20260909-demo-mode.md` のデモモードで足りる~~
  **訂正（2026-09-16）: 足りない。** デモモードは `VITE_DEMO_MODE` で切り替わる Web 版だけの
  仕組みで、申請物である `expo-prototype/` には実装が無い。審査担当が触るのは iOS アプリなので、
  **本番に審査用の実アカウントを作って ID/パスワードを審査メモに書く**必要がある。
  これを落とすと Guideline 2.1 の直撃（`docs/app-store-submission.md` 6章・7章）。
  判定の3問の①「直さないと審査で落ちるか」に当たるので、**出す前に直す**側

## プレモータム

1. **worker アカウントを作っても、現場が使わない。** → その場合でも「入力UIが悪いのか、
   渡し方が悪いのか」を初めて切り分けられる。今は切り分け以前に材料が無い
2. **Apple Developer 登録で法人名義が必要になり D-U-N-S 待ちになる。** → 個人名義で出す。
   組織向けの限定配布（Unlisted / Custom App）は公開後に検討できる
3. **凍結したのに配置の話が再燃する。** → 再燃したらこのログを読み、`entry_point` の
   件数を先に数える。n が足りていなければ議論しない
4. **n≧30 が永遠に来ない。** → 1 と同じ根で、その場合は撤退条件そのものを見直す材料になる
