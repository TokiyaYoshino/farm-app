# RLS を先に適用し、kishu/asuka の分離は次段にする

日付: 2026-09-03
状態: 決定（実行はユーザー側の Supabase 操作待ち）

## 背景 / Why

`docs/handoff-input-redesign.md` 2.6章は、塞ぐ順序を
**「① organizations の確認 → ② organization_id の振り直し → …→ ⑤ RLS 適用」**と書き、
冒頭にも「**RLS を先に流しても分離されない**。必ず 0. のデータ振り直しが先」と置いている。

理由は正しい。全ユーザーの `organization_id` が同一値（`2026-07-22-organization-id-columns.sql`
が全行を kishu の id でバックフィルしたため）なので、RLS を入れても kishu と asuka は
互いのデータを見られる状態が続く。

ただしこの順序のまま**2026-08-09 から3週間以上止まっている**。振り直しは本番データの
更新で承認が要り、`org` 文字列と `organization_id` の二重基準の解消（コード変更）も伴うためで、
その間ずっと **anon キーだけで `users` 5件・`reports` 33件などが素で読める状態が続いている**。

## 決めたこと

**RLS 実ポリシー化を先に適用する。** kishu/asuka の分離（organization_id の振り直し）は
その次の独立したタスクとして扱う。

### 理由

2つは**独立した穴**であり、順序に依存関係が無い。

| | 塞ぐ相手 | 現状 | RLS 適用で |
|---|---|---|---|
| 穴A: 匿名の直読み | **誰でも**（anon キーは公開JSに入っている） | 全テーブル素で読める | **塞がる** |
| 穴B: kishu ⇄ asuka | 自組織のログインユーザー | 互いに見える | 変わらない（悪化もしない） |

穴Aのほうが圧倒的に広く、App Store 申請のブロッカーもこちら（`docs/app-store-submission.md` 前提1）。
穴Bは「今日ログインできる6人の中での越境」で、RLS を後回しにする理由にはならない。

### 順序を入れ替えても壊れない根拠

適用時点では全員の JWT の `organization_id` が同一値、かつ全行の `organization_id` も同一値なので、
**RLS の判定は全員 true になる＝アプリの見え方は今日と1ミリも変わらない**。
クライアントは従来どおり `org` 文字列（crops/fields/reports/settings/pesticides/projects）と
`organization_id`（users/schedules/comments）で絞り続ける。

振り直しを先にやると、逆に `users`/`schedules`/`comments` だけが即座に分離され、
`org` 文字列で絞る表とのねじれが**先に**表に出る。RLS を先に入れておけば、
振り直しはその後「全表の `organization_id` を `org` に合わせて更新する1回の作業」に閉じる。

## 検討した代替案

- **ドキュメントどおり振り直しを先にやる** → 却下。承認と code 変更を待つあいだ穴Aが開き続ける。
  3週間止まった実績がある
- **同じセッションで両方やる** → 却下。壊れたときにどちらが原因か切り分けられない。
  rls-rollout.md 自身が「1テーブルずつ・そのつど確認」と決めている方針とも合わない
- **RLS を入れず asuka を別プロジェクトに分ける** → 却下。マルチテナント化の設計（ADR-001）を捨てることになる

## 影響範囲

- **DB / 権限**: RLS ポリシーの全面適用。`allow_all` を撤廃し `organization_id = jwt_organization_id()` へ
- **既存機能**: 見え方の変更なし（上記の根拠）。ただし**全員が再ログインするまでデータが見えなくなる**ため、
  手順2（Auth Hook 有効化 → 再ログイン）を飛ばせない
- **ストア審査**: 申請の前提1が満たされる
- **残る穴**: kishu ⇄ asuka の相互閲覧、`work_categories` の全組織共有。どちらも**今日と同じ**

## プレモータム（半年後に失敗していたとしたら）

1. **「RLS を入れたから安全」と思い込み、振り直しを永久に後回しにした。** 穴Bは残ったまま
   3社目を受け入れてしまう。→ ロードマップの「進行中」に穴Bを残し、2組織目を**正式に**
   受け入れる前の必須条件として書く
2. **再ログインを全員に届けられず、「データが消えた」と言われた。** 5人とも admin で連絡はつくが、
   Expo アプリ側のログアウトを忘れると片方だけ壊れる。→ 手順2にアプリを明記済み
3. **`users` のブロックでログイン不能になった。** 匿名の列権限を絞る箇所が唯一の全機能停止リスク。
   → 適用順を最後にし、切り戻し1文を手元に置いてから流す（rls-rollout.md 手順6・切り戻し基準）
