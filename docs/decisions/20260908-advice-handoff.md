# 相談から記録・写真へ橋を架け、畑全体でも農薬の使用回数に答えられるようにする

- 日付: 2026-09-08
- 状態: 採用
- 種別: 仕様変更（機能6＝作物ごとの相談／畑全体の相談の拡張）

## 課題（Why）

`docs/decisions/20260906-general-advice-entry.md` で「ホーム用の汎用AIアシスタントが欲しい」という要求を2つに分解した。作物非依存化（畑全体の相談）は同日に実装したが、もう一方の「入口を1つにまとめたい」は**対象セレクタを付けただけ**で終わっている。同ADRのプレモータム3が、その未完部分を自分で名指ししている。

> **入口を1つにしたのに、結局どこから何ができるか分からないままだった。** 相談・記録に聞く・写真で診断が別々の入口のままで、「相談する」を押した人が記録検索の用事を果たせずに終わる。→ 統合したのは相談の対象選択だけで、**機能間の橋渡しは今回やっていない**

相談をホームの主操作（1画面1個の primary ボタン）に格上げした以上、そこを押した人が持ち込む用事は3種類ある。いま果たせるのは1つだけ。

| 用事 | 例 | 改修前 |
|---|---|---|
| 知識の用事 | 「今なにをすべき？」 | 果たせる |
| 記録の用事 | 「先月何回撒いた？」「この農薬あと何回使える？」 | 別入口（記録タブの検索欄に文字を入れないと現れない） |
| 写真の用事 | 「この葉、何の病気？」 | 別入口（診断結果を相談へ持ち込めない） |

とくに「あと何回使えるか」は、`docs/decisions/20260805-pesticide-precheck.md` で作った**法的義務（使用基準の遵守）に直結する集計**が既にあるのに、相談からは一切見えていなかった。防除助言は散布履歴を、記録検索は使用回数を受け取っているのに、差別化の中核である相談だけが受け取っていない——`20260906-advice-reply-tone.md` で一度直したのと同じ形の穴が、農薬について残っていた。

## 決めたこと

相談の窓に持ち込んだ3つの用事が、そこで完結するか、そこから正しい場所へ渡るようにする。3つは性質が違うので、同じ機構では解かない。

| 用事 | ボトルネック | 解き方 |
|---|---|---|
| 農薬の実績 | 材料が渡っていない | **材料を渡す**（`pesticideUsage` フィールド。スキーマ変更なし） |
| 記録の検索 | 「いつ記録を見るべきか」の判断と検索語が要る | **strict スキーマに枠を作る**（`record_search_query`） |
| 写真 | 入力は利用者が持っている。判断は不要 | **UIの導線＋材料フィールド**（`photoDiagnosis`。LLMの判定枠は作らない） |

写真に判定枠を作らないのが要点。「写真を撮ってください」はモデルが最も安易に出す提案で、枠を作れば過剰に出る。写真は利用者しか用意できないので、常設ボタンで足りる。

### 畑全体の相談でも農薬の使用回数に答える（過去判断の部分的な上書き）

`20260906-general-advice-entry.md` は、畑全体の相談では作物が定まらず適用情報を照合できないため、`isGeneral` 分岐で**薬剤の具体値に一切触れさせない**と決めた。今回そのうち**使用回数だけを解禁する**。

理由: 「あと何回使えるか」は作付け単位で `summarizeUsageByCrop` が数えた**自農場の実績**と、ラベル（FAMIC登録適用部）の**原文の上限**であって、作物を指定しないと判断できない性質の情報ではない。むしろ畑全体の相談は「どの作付けで何回使ったか」を横断で見られる唯一の場所で、ここで答えられないのは実務上いちばん惜しい。

述べてよい範囲は両モードで同一（＝回数）に揃え、違うのは適用情報ブロックの有無だけ、という形にする。

| | 作付けの相談 | 畑全体の相談 |
|---|---|---|
| 使用回数（記録から算出） | ○ | **○ ← 今回変更** |
| 総使用回数の原文「6回以内」 | ○ | **○ ← 今回変更** |
| 「超過の疑い」の警告 | ○ | **○ ← 今回変更** |
| 希釈倍数・使用方法・適用のある病害虫 | ○（登録情報の原文のみ） | ×（据え置き） |
| 使用の可否・薬剤の推奨 | ×（据え置き） | ×（据え置き） |
| 「あと◯回使える」 | **× ← 新規に明文で禁止** | **×** |

### 「あと何回使えるか」は計算させない

利用者の用事は「あと何回使えるか」だが、`残り = 上限 − 実績` は**出力させない**。

- `src/components/PesticideUsageSummary.tsx` の画面表記は「総使用回数の上限 6回に対して、集計期間の実績 3回です（使用の可否を示すものではありません）」。**画面は意図的に残り回数を出していない**。相談だけが「あと3回使えます」と言えば、AIと画面が食い違い、しかも食い違う方向が「許可」側になる
- 「あと3回」は使用時期・使用方法・同じ成分を含む別の剤・記録漏れをすべて無視した数字で、`20260805-pesticide-precheck.md` の非対称性（「超過の疑い」だけを警告し「OK・安全」とは言わない）に正面から反する

**実績と上限の2つの数字を並べて返せば用事は満たせる。** 禁じるのは許可の言い回しだけ。

## 検討した代替案

- **`aggregates`（既存4000字枠）に農薬の実績を混ぜる** → 見送り。サーバーは `aggregates` の中身を知らないので、農薬が入っているかを判定できず、`isGeneral` の書き分けも `limits`/`sources` の出し分けもできない。文字列を覗いて判定するのは「整形はクライアント、APIは文字列を受け取るだけ」の疎結合を壊す
- **サーバー側で使用回数を数える** → 却下。`api/` は Supabase に触らない設計なので作業記録を持っていない
- **`needs_record_search: boolean` だけをスキーマに足す** → 見送り。検索語が無いと記録検索に渡すものがなく、価値の中心（語）が落ちる
- **記録検索への導線を静的ボタンとして常設する（スキーマ変更なし）** → 見送り。「いつ記録を見るべきか」の判断が利用者に残り、プレモータム3が解けない
- **写真の診断結果を `messages` に user メッセージとして混ぜる** → 却下。画像診断の出力は**LLMの推定**であって利用者の申告ではない。user 発言に入れると「べと病である」が確定事実として洗浄され、`limits` を付ける場所も無くなる（`api/advise.ts` 冒頭の「情報源を3つに分け、どこから来た情報かを必ず区別する」に反する）
- **`photo_suggested: boolean` をスキーマに足して写真を促させる** → 却下。モデルが最も安易に true にする枠で、過剰ルーティング問題を2箇所に増やす
- **現状維持（実利用の母数が貯まるまで待つ）** → 見送り。本番の `ai_outputs` は全11件が開発時の動作確認で母数がゼロ。待っても材料は増えない

## 影響範囲

- **DB / 権限**: `crop_advice_messages` に `record_search_query text`（nullable）を1列追加（`scripts/migrations/2026-09-08-crop-advice-record-search.sql`）。RLS は `organization_id = jwt_organization_id()` で列を見ていないため変更不要。Expo 版の insert も列を含めないだけで壊れない
- **既存機能**: 削除なし。記録検索チャット・写真診断・日報・防除助言はいずれも入口・挙動とも従来どおりで、相談から**開く経路が増えるだけ**
- **`/api/search-chat`**: `formatPesticideUsageForPrompt` に `includeLabelRows`（既定 true）を足すが、既定のままなので出力は一字一句変わらない。回帰テストで固定する
- **原価**: 相談1回あたり約1500トークン（≒ $0.0002）増える。`docs/roadmap.md` の Free 日次上限は設計のみで未実装のままなので、利用が伸びれば素通しでコストが出る（`20260906-general-advice-entry.md` プレモータム2の継続）
- **ストア審査 / 規制・業界固有の実務**: 農薬取締法の使用基準（総使用回数）に関わる情報を扱う範囲が広がる。ただし**判定は非対称のまま**（「超過の疑い」のみ警告し、可否・安全は言わない）で、製品ラベル確認の促しも維持する。数値は LLM に生成させずコードが数えた値とラベル原文しか渡さない

## プレモータム（半年後に失敗していたとしたら、何が起きたか）

1. **枠を作ったら入れたがった。** `record_search_query` を足したことで、相談で答えられる質問にまで「記録を調べる」ボタンが出て、利用者が毎回2回操作させられる機能になった。→ `follow_up_question` のときと同じ「置き場のある方へ行く」現象。プロンプトの縛り・サーバー側の握りつぶし（記録が無ければ null／聞き返しがあるなら null）・契約テストの3重で抑えるが、実利用の出現率は `ai_outputs.output_json` で後から測って調整する
2. **畑全体で回数を許したことが、可否の質問を呼び込んだ。** 回数を語れるようになったぶん会話が希釈倍数・使用可否へ伸び、limits を読み飛ばした利用者が一般論を自分の圃場の基準として受け取る。→ `20260906-general-advice-entry.md` プレモータム1の延長。**禁止文と limits を契約テストで固定するのが唯一の歯止め**
3. **写真を持ち込めるようにしたのに、診断の精度が変わらないので体験も変わらなかった。** 橋を架けただけで、渡した先の中身（画像診断の当たり具合）は改善していない

## 過去の判断との関係

- `docs/decisions/20260906-general-advice-entry.md`: プレモータム3への回答。「AIタブは作らない」（`20260823-ai-information-architecture.md`）は**覆さない** —— 入口は増やさず、既にある相談の窓から他機能へ渡す形にした。一方で「畑全体では薬剤の具体値に触れない」は**使用回数についてのみ上書きする**（理由は上記）
- `docs/decisions/20260805-pesticide-precheck.md`: 非対称な判定（「超過の疑い」のみ警告し「OK・安全」とは言わない）を維持し、さらに「あと◯回使える」の禁止として明文化した。範囲を広げる方向の変更ではない
- `docs/decisions/20260906-advice-reply-tone.md`: 「コードが計算した事実を渡す」の続き。あのとき散布履歴・作業回数は渡したが、農薬の使用回数だけが残っていた。案E（記録の薄い作付けに他の作付けの記録を渡す）が誤帰属リスクで取り下げられたのを踏まえ、**作付けの相談では対象作物の集計だけを渡す**（畑全体は全作物）
- `docs/decisions/20260829-ai-output-structure.md`: 結論を1文目に置く原則、出典・限界を毎回付ける原則は維持
- `docs/decisions/20260823-ai-wording-outcome-based.md`: UI文言に「AI」を出さない。ボタンは「記録を調べる」「写真で調べる」「この結果をもとに相談する」
- 矛盾・上書きは上記2件（畑全体×農薬の回数、「あと◯回」の明文禁止）のみ

**未検証**:

- **実モデルでの挙動**。`20260906-advice-reply-tone.md` の実測で「**渡すだけでは使わない**」ことが分かっているので、次の4点は実 API で目視確認する必要がある（Supabase ログインが要るためオーナーが実施）:
  1. 畑全体で「ダコニールはあと何回使える？」→ 実績と上限を並べて答え、「あと3回使えます」とは言わず、希釈倍数に触れない
  2. 畑全体で「去年の秋は何回防除した？」→「記録を調べる」ボタンが出る
  3. 「摘果のやり方は？」→ ボタンが**出ない**（過剰ルーティングの確認）
  4. 写真診断 →「この結果をもとに相談する」→ 候補を「可能性」として扱い、確かめ方を示す
- **Expo は実機での往復**（起動確認をしていない）
- **実利用での効果**。`ai_outputs` の呼び出し実績は開発時の動作確認のみで、比較の母数が無い（`20260906-general-advice-entry.md` と同じ制約）。ただし `record_search_query` は `output_json` に、写真の有無は `input_summary` に残るので、母数が貯まれば過剰ルーティング率と利用実態を後から SQL で測れる
