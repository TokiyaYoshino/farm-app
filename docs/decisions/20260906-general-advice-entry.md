# 相談の入口をホームの主操作に格上げし、作物を指定しない「畑全体の相談」を追加する

- 日付: 2026-09-06
- 状態: 採用（Web版のみ実装。Expo版は据え置き）
- 種別: 機能追加（既存機能の拡張）＋仕様変更（情報設計・導線）

## 課題（Why）

「ホーム用の汎用AIアシスタントが欲しい」という相談から。掘り下げると要求は2つに分かれた。

1. **入口を1つにまとめたい** — AI機能が各所に分散していて、どこから何ができるのか分かりにくい
2. **農業エージェントを汎用化したい** — 作物ごとの相談は、作物を登録していないと入口すら出ない

加えてオーナーの指摘が1つ。**「AIが結局いちばんの差別化になるので、その操作をより明確で分かりやすい場所に置かないともったいない」**。

これは実態と合っている。`docs/spec-ai-features.md` 8章の競合比較では、AI6機能のうち市場での根拠が最も強いのは農業エージェント（機能6）で、競合レビュー89件で唯一記録された「削除理由」（種まき日を入れても今後の作業を教えてくれない）に直接対応する。にもかかわらず、その入口は次の状態だった。

| 現状 | 問題 |
|---|---|
| ホームの「作付け中 — 相談できます」カードの小さな行 | 差別化の中核が、天気カードや今日の一手より下の一覧に埋もれている |
| 表示条件が `crops.length > 0` | **作物を1件も登録していないと、入口自体が存在しない** |
| スレッドは `crop_id` 必須 | 「畑全体で今なにをすべきか」のような、作物にまたがる相談ができない |

3つ目が効いている。新規利用者は作物を登録する前に相談したい（何を作るか・いつ始めるかを相談したい）のに、相談するには先に作物を登録する必要があった。

## 決めたこと

### 1. `crop_id` を nullable にし、null を「畑全体の相談」とする

`crop_advice_messages` / `crop_advice_actions` の `crop_id` から NOT NULL を外す（`scripts/migrations/2026-09-06-crop-advice-general-thread.sql`）。作物ごとのスレッドはそのまま維持し、null のスレッドを1本足すだけにする。

| | 作物ごとの相談 | 畑全体の相談 |
|---|---|---|
| 対象 | 1つの作付け | 農場全体・作物にまたがる話 |
| 農薬の登録情報 | FAMIC の適用情報を照合して原文を返す | **照合しない**（作物が定まらないため）。作物を選ぶよう促す |
| 作付け日・生育段階 | 経過日数から推定 | 使わない |
| 記録の照合 | その作付けの記録だけ | 作物を絞らず全記録 |
| 保存先 | `crop_id = 作物ID` | `crop_id = null` |

### 2. ホームの「作付け中」カードを「相談する」カードへ格上げする

新しいカードは作らず、既存カードを作り替える。理由は2つ。

- `docs/decisions/20260823-ai-information-architecture.md` が「今日の一手」を**主役としてホーム上部に置いた**ばかりで、その上に別カードを差し込むのは直近の判断の上書きになる
- 同ADRの実測でホームは既に**カード7枚・全長1,081px（1.3画面）**。8枚目を足せば縦に伸びる

格上げの中身は、見出しを「相談する」に変え、`btn("primary","lg")` の主操作ボタンを最上部に置き、その下に従来の作付け一覧（やること件数バッジつき）を残す。表示条件から `crops.length > 0` を外し、**作物0件でも常に出す**。ホーム内の primary ボタンはこれ1個だけにする（`CLAUDE.md`「primary＝主操作、1画面1個」）。

### 3. ボタンの行き先は状況で振り分け、ラベルに行き先を書く

| 作物の数 | ボタンのラベル | 行き先 |
|---|---|---|
| 0件 | 畑のことを相談する | 畑全体 |
| 1件 | 〇〇のことを相談する | その作付け |
| 2件以上 | 畑全体のことを相談する | 畑全体（作物ごとは下の一覧から） |

**目立つ入口を、常に畑全体（＝農薬の登録情報を照合できない弱い方）へ固定しない**ためにこうした。作物が1件なら毎回選ばせる必要はなく、複数あるなら下の一覧から選べる。ラベルに行き先を書けば説明文は不要になる（`docs/decisions/20260824-no-manual-test.md` の「まず書かずに済ませる」）。

### 4. シート内に対象セレクタを置く

相談シートの上部に「相談する対象」（畑全体／各作物）の `select` を置き、切り替えるとそのスレッドを開き直す。これが「入口統合」の答えになっている——**入口は1つ、対象の選択はシートの中**。チップ行にしなかったのは、作物が増えると横スクロールになり、上記ADRが問題視した形そのものになるため。

### 5. 安全側の設計は畑全体でも維持する

農薬の希釈倍数・使用回数を LLM に生成させない原則は変えない。畑全体では作物が定まらず適用情報を照合できないので、`api/advise.ts` は次を強制する。

- 適用情報を渡されても、作物未指定なら**プロンプトに載せない**（`isGeneral` で握りつぶす）
- system プロンプトで「特定の作物を前提にした具体値を述べず、作物を選んで相談し直すよう促す」ことを指示
- `limits` に「作物を指定していない相談のため、薬剤の使用可否は判断していません」を必ず付ける

契約テスト（`scripts/test-advise.mjs`）に上記を検証するケースを追加した（この時点で 89 assertions / 全通過。同日の `20260906-advice-reply-tone.md` で 97 に増えている）。

### 6. Expo版は変更しない

全体相談はまずWeb版だけに出す。`expo-prototype/lib/store.tsx` は `.eq("crop_id", cropId)` で引くため null 行は現れず、Expo版は壊れない。両版に同じ実装を重複させる前に、Webでの利用実績（`ai_outputs`）を見てから移植を判断する。

## 検討した代替案

- **案B: 「AI」タブ／AIメニューを新設して全機能を集約する** → 却下。`docs/decisions/20260823-ai-information-architecture.md` が実測と外部調査（NN/g の Amazon Rufus 調査）から「AIを独立させるほど『わざわざ行く場所』になり使われない」と結論した判断と正面から反する。今回の要求「入口をまとめたい」は、**1つの入口から対象を振り分ける**形（決めたこと3・4）で満たす
- **案C: 新カードを作り、今日の一手カードの上に置く** → 却下。直近ADRが主役として置いた位置を奪い、ホームのカードが8枚目に増える（上記）
- **案D: 相談前に作物の仮登録をさせる** → 却下。相談したい瞬間に登録作業を挟むのは、`20260824-no-manual-test.md` の「そもそも聞かない」に反する。作りたい作物を決めるための相談ができなくなる
- **現状維持** → 却下。差別化の中核が一覧に埋もれ、作物0件では存在しない状態が続く

## 影響範囲

- **DB / 権限**: `crop_advice_messages` / `crop_advice_actions` の `crop_id` を nullable 化（2026-09-06 に本番へ適用済み）。RLS は変更不要 —— 本番の実ポリシーは `organization_id = jwt_organization_id()` で作物を見ていないため、**`crop_id` が null の行も問題なく読み書きできる**（同日にポリシー定義で確認）
- **既存機能**: 削除なし。作物ごとのスレッド・今日の一手・記録検索チャット・写真診断はいずれも未変更。ホームは「作付け中」カードの見た目が変わるだけで、作物行からの導線は従来どおり
- **照合ロジック**: `src/lib/adviceMatch.ts` の `reportMatches` に「`crop_id` が null なら作物で絞らない」分岐を追加。これが無いと畑全体の「やること」が永久に「まだ」のまま残る
- **ストア審査 / 規制・業界固有の実務**: なし。農薬に関する注意書き・製品ラベル確認の促しはすべて維持（上記5）
- **既知のギャップ（今回の範囲外）**: 分析タブの AI 出力履歴は `kind` 4種のみ対応で、`advice` 種別は元から表示されない（`docs/spec-ai-features.md` 4章）。畑全体の相談も同様に履歴に出ない

## プレモータム（半年後に失敗していたとしたら、何が起きたか）

1. **畑全体の相談が「何でも聞ける窓」に見え、農薬の踏み込んだ質問を招いた。** limits を読み飛ばした利用者が、作物を特定しない一般論を自分の圃場の基準として受け取る。→ プロンプト・limits の両方で作物を選ぶよう促してはいるが、**入口が目立つほどこのリスクは上がる**。実際の質問内容を `ai_outputs.input_summary` で見て、農薬に関する質問が畑全体に偏るようなら、対象セレクタの初期値や誘導文言を見直す
2. **原価が想定より膨らんだ。** ホーム最上位の主操作にしたことで呼び出しが増えるが、~~`docs/roadmap.md` の Free 日次上限は設計のみで**未実装**。マルチテナント化＋課金連携が済むまで上限が効かないため、利用が伸びるほど素通しでコストが出る~~ **訂正（2026-09-17）: 実装済み。** 2026-09-10 の Web版リリースで `api/_auth.ts` の `checkDailyLimit` が入っている（画像診断20回/日・その他50回/日・fail-open）
3. **入口を1つにしたのに、結局どこから何ができるか分からないままだった。** 相談・記録に聞く・写真で診断が別々の入口のままで、「相談する」を押した人が記録検索の用事を果たせずに終わる。→ 統合したのは相談の対象選択だけで、機能間の橋渡しは今回やっていない

## 過去の判断との関係

- `docs/decisions/20260823-ai-information-architecture.md`: 「AIタブ」「AIメニューは作らない」という決定を**覆さない**。独立したチャットタブは作らず、ホームの文脈内に置いたまま視認性だけを上げる、その延長線上の変更。同ADRの未着手項目「農業エージェントの Web 版移植」は既に完了しており、本件はその次段にあたる
- `docs/decisions/20260823-ai-wording-outcome-based.md`: UI文言に「AI」を出さない方針を踏襲。ラベルは「相談する」で統一した
- `docs/decisions/20260810-next-action-advice.md`: エージェントとして成立する3条件（会話として続く・作付けごとに溜まる・作業記録と照合できる）は畑全体の相談でも維持している（照合は作物を絞らない形に変えた）
- `docs/decisions/20260824-no-manual-test.md`: 説明文を足す前に「書かずに済ませる方法」を採り、行き先をボタンのラベルに書いた。説明文は作物0件のときの一行だけ
- 矛盾・上書きする判断はなし
