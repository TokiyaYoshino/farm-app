# 相談の質を「賢さ」ではなく「接地の可視化」で上げる

- 日付: 2026-09-10
- 状態: 提案（未着手・オーナー承認待ち）
- 種別: 仕様判断（AI機能の中身）＋段階的な実装計画
- 根拠: [`docs/research/ai-agent-ux-differentiation-2026-09.md`](../research/ai-agent-ux-differentiation-2026-09.md)（**外部事例は一次情報未確認。確度の印を必ず読むこと**）、`api/advise.ts` の実測

## 課題（Why）

オーナーの認識: 「同じような農業アプリが多くある中で、**自分の記録をもとにベストプラクティスを出し、外部の情報も取ってきて最善策を探る**ものは無い。この点の質を求めたい」。

コードを読むと、**その"質"は今のところ存在しない**。

- `api/advise.ts` は `gpt-4o-mini` の**単発呼び出し**。道具は0件で、モデルが自分で調べに行く経路が無い
- 外部の一般知識は **LLMの内部知識**から出ており、出典が無い。ChatGPT に聞くのと質的に同じ
- 一方で `adviceMatch`（やることと作業記録の照合）・`pesticideUsage`（非対称判定）・スレッド蓄積という**他社に無い資産は既に動いている**

つまり課題は「AIが賢くない」ではなく、**接地している事実が画面に出ていない**ことと、**取れている外部情報をモデル自身が引けない**ことの2つ。

## 決めたこと（提案）: 3段階。段階1と2を推す

### 段階1 — 接地を画面に出す（API変更なし・数日）**← 最優先**

回答カードの構成を固定する。上から順に:

1. **結論1文**（現状どおり）
2. **やること**（照合バッジ付き。既存・最大の資産）
3. **見ておく点**
4. **根拠**（折りたたみ・見出しは体言止め「使った材料」）— **自分の記録n件（期間）／天気14日／登録農薬m行**を件数で出す。防除助言の「使った天気を見る」を相談スレッドにも広げる形
5. **判定できないこと**（既存 `unknowns` / `limits`）
6. **続きの問い 3つ**（押すと次の質問になるチップ）

あわせて2点:

- **出所の二層表示。** 「あなたの記録では」に相当する部分と、一般的な目安を**視覚的に分ける**（記録＝`inkSoft` の淡塗り、外部・一般＝`info`。同じ緑にしない）。トークンは `src/ui/tokens.ts` から取る
- **空のスレッドを出さない。** 開いた直後に「今日の状況」を1枚（作付けn日目 / 前回散布からm日 / 週末の降雨）＋質問チップ3つ。**利用者は質問文を自分で書かない**

**この段階だけで、体感の質はいちばん動く。**「調べてから答えている」ことが初めて画面に出るため。

### 段階2 — 渡すのをやめて、引けるようにする（`api/advise.ts` の道具化・1〜2週）

単発呼び出しを **tool calling ループ**に変える。道具は**新規に作らない**。今クライアントが手で組み立てているものを、そのまま道具にする:

`search_records` / `spray_history`（`pesticideUsage.ts`）/ `pesticide_registrations`（`api/pesticide-registration.ts`）/ `weather`（Open-Meteo）

- 「探る」が成立するのはここから。**必要な材料はほぼ全部すでにある**
- 応答は遅くなる。**進捗を実況する**（「記録を14件見ています」）。遅さは実況で買う
- コストは上がる。日次上限（`checkDailyLimit`）は**道具ループの反復回数にも上限を置く**（1相談あたり最大5回など）

### 段階3 — 病害虫発生予察情報（**保留・今回は着手しない**）

`docs/decision-log.md` 2026-07-31 の「予察情報はPDFのみでAPIが無く自動化が脆いため分離」という判断を**覆さない**。覆すだけの新事実（安定して取れる経路）を今回確認できていない。段階2が終わってから、取得経路の実物検証だけ先に行う。

## 検討して採らなかった案

- **モデルを上位に替える（`gpt-4o-mini` → 上位モデル）。** 一般知識の質は上がるが、**出典の無さは変わらない**。差別化されない部分にコストを払うことになる。段階2の後に、効果を測れる状態で検討する
- **「AI」を前面に出した訴求に戻す。** 2026-08-23 の判断（成果ベースの文言）と正面から衝突する。覆す理由が無い
- **相談タブの外に「調べる」画面を新設する。** 入口を増やす方向で、2026-09-09 の集約と矛盾する

## 影響範囲

| 対象 | 段階1 | 段階2 |
|---|---|---|
| DBスキーマ | 変更なし | 変更なし（道具の呼び出し記録を残すなら `ai_outputs` に列追加を検討） |
| RLS | 影響なし（`allow_all` の課題は別件・配布前に必須） | 同左 |
| `api/advise.ts` | 変更なし | **書き換え**（レスポンス形式は維持する。壊すと過去の保存が読めなくなる） |
| Expo版 | 未反映のまま（Web先行の方針どおり） | 同左 |
| コスト | 変わらない | **増える。** 反復上限で頭を押さえる |
| 規約 | 見出しは体言止め・ボタンは動詞・入口に「AI」を出さない・アイコンの重複禁止（`CLAUDE.md`）を守る | 同左 |

## 計測（段階1と同時に入れる）

情報設計の変更が「効果は未検証」で終わる失敗を3回繰り返している。**先に測る口を置く。**

- 「使った材料」を開いた回数 / 相談の回答表示回数
- 続きの問いチップのタップ率
- 質問チップ経由の相談開始率（空スレッドが埋まったか）

**判定**: 30日で「使った材料」を一度も開かない利用者が大半なら、P1/P2（出典の可視化）は farm-app の利用者には効いていない。その場合は畳むのをやめて**回答本文に件数を1行で埋める**方向に切り替える（撤退ではなく形の変更）。

なお相談タブ自体の撤退条件（`thread` + `thread_tool` が20%未満なら降ろす）は [`20260909-advice-tab-keep-with-exit-criteria.md`](20260909-advice-tab-keep-with-exit-criteria.md) のまま**据え置く**。今回の変更はその判定期間中に入るので、**判定時には「段階1適用後の30日」で測ること**を明記しておく。

## 前提の弱点（プレモータム）

1. **外部事例が一次情報未確認。** 3章の事例が事実と違えば、P1〜P8 の一部は根拠を失う。→ 研究ドキュメント6章のチェックリストを、ネットワークが使えるときに先に消化する
2. **接地を見せても読まれない可能性。** 高齢の利用者に「根拠を開く」操作は重い。→ 上の計測で判定し、本文への1行埋め込みに切り替える
3. **道具化で回答が遅くなり、相談タブの利用率がむしろ下がる。** → 実況表示を段階2と同時に入れる。上限も同時に置く
4. **`OPENAI_API_KEY` が Vercel Production に無い疑いが未解消。** これが未設定なら段階1も段階2も本番で動かない。→ **着手前に確認する**（`docs/releases/2026-09-10-web-ai-consolidation.md` の残タスク）
