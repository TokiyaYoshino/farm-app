# AI導線の配置：Web を配置の正とし、Expo を追従させる

- 日付: 2026-09-08
- 状態: 一部採用（プラットフォームの正・Expo 追従・効果測定は決定。相談の窓の内側は未決）
- 種別: 仕様変更（情報設計・導線）

## 課題（Why）

汎用AIアシスタント（相談の窓）の機能面が実装され、残るのは配置だけになった。
ところが配置を詰めようとすると、**同じアプリの配置が Web と Expo で食い違っていて、
どちらに対して判断しているのかが決まらない**。先にそこを決める。

## 実測した乖離（`origin/main` = 31ed127 時点）

2026-08-23 の情報設計・第1段階は **Web にしか入っていない**。Expo は 2026-08-02 の
移植時点のまま止まっている。

| 第1段階でやったこと | Web (`src/App.tsx`) | Expo (`expo-prototype/`) |
|---|---|---|
| 記録一覧のボタン行を出力系2つに絞り `flexWrap` で折り返し | 済 (`:3061`) | **未**（3ボタンを `ScrollView horizontal`、`ReportScreen.tsx:211`） |
| 「記録に聞く」を検索の文脈へ移す | 済 (`:3076`) | **未**（独立ボタンのまま、`ReportScreen.tsx:219`） |
| 写真の直下に「この写真で病害虫を調べる」 | 済 (`:3153`) | **未**（記録一覧のボタン行のみ、`ReportScreen.tsx:222`） |
| ホームに「写真で病害虫を調べる」（記録を伴わない経路） | 済 (`:2713`) | **未** |
| （第1段階外）帳票出力 | 済 | **未** |

Expo 側のコメントは `件数＋AI機能ボタン群（Web版と同一の並び）` と書いてあるが、
第1段階以降これは事実と違う。

## 決めたこと

### 配置の正は Web 版。Expo は追従する

2026-08-01 の Expo 検証が決めた向き（「リデザインではなく移植」＝ Web が設計・Expo が写し）を
**そのまま維持する**。今回それを明示的に再確認した。

理由:

- 第1段階は NN/g の AI 発見性調査を根拠に決めた変更で、Expo の現状（横スクロールの3ボタン行）は
  その調査が「密な行への埋没」と名指しした形そのもの。Expo を正にすると、根拠のある変更を
  根拠なく戻すことになる
- `api/*` は Web/Expo 共通のため、追従に必要なのは UI の移植だけ

### ただし「設計は Web・出荷は Expo」の非対称が残ることを明記する

正式リリースは Expo ネイティブ（WebView ラップは審査ガイドライン 4.2 でリジェクト、
`docs/decisions/20260801-verify-expo-dashboard-report-prototype.md`）。
**設計を決める場所と出荷する場所が違う**という状態がこの決定の副作用として残る。

今回の乖離は、第1段階を Web に入れて Expo に入れなかったことで発生した。同じことを防ぐため、
**画面配置に触る変更は Web と Expo を同じ作業単位で扱う**（片方だけ先に入れない）。
今回の相談の窓の配置も、Expo への移植までを1つの単位とする。

### `ai_outputs.entry_point` を足して、置き場所の効果を測れるようにする（実装済み）

情報設計の変更は今回で3回目だが、3回とも「効果は未検証」で終わっている。原因は母数の
少なさ（本番ユーザー5人・全員 admin、記録18件）だけではなく、**そもそも測る手段が無い**こと。

`kind` では代用できない。Web版の AI 起点は9つあり、うち3つが同じ `kind='diagnosis'` を
吐くため（記録一覧の写真直下 / 記録詳細シート内 / ホームの単体診断）、`kind` だけでは
「どの置き場所が効いたか」が原理的に分離できない。

- `scripts/migrations/2026-09-08-ai-outputs-entry-point.sql`（**未適用**）
- `saveAiOutput` の payload に `entryPoint` を**必須**で足した。任意にすると導線を
  足したときに書き忘れ、「その導線は使われていない」と読めてしまい集計が嘘になる。
  必須なら型エラーで気づく
- 値は `AiEntryPoint` 型（`src/App.tsx`）が正。**導線を動かしたら新しい値を足す**。
  既存の値の意味を変えると、変更前後の比較というこの列の唯一の用途が壊れる

あわせて2件、この列を入れる過程で見つかった欠落を直した。

1. **「記録に聞く」が `ai_outputs` に一切残っていなかった。** 2026-08-23 第1段階の要は
   「検索窓との統合」で、まさにこの導線なのに、記録が無いので効果を測りようがなかった。
   `kind='record_search'` として保存する。`api/search-chat.ts` は `usage` / `costUsd` を
   返していたが呼び出し側が捨てていたので、コストも今後は残る
2. **分析タブの `KIND_LABEL` に `advice` が無く**、作物の相談の行は種別が空欄で
   表示されていた（`src/components/AnalyticsView.tsx`）。`record_search` を足すと
   同じ欠落が2件になるため、両方を追加した

なお、この列を読む画面は作っていない。母数がゼロの今は SQL 1本で足り、
UI を作るのは実績が溜まってからで遅くない（集計クエリは移行SQLの末尾にコメントで置いた）。

### Expo の追従は「今回の配置変更」より先に行う

先に第1段階の5項目（上の表）を Expo に移植する。これを飛ばして相談の窓だけ入れると、
Expo だけ「相談の窓はあるのに、記録一覧のボタン行は横スクロールのまま」という
最も筋の悪い状態になる。

### 論点1について（保留の理由）

「起点が3つ並んでいるから減らす」は、2026-08-23 の「AIを1か所に集めるほど使われない、
**意図の生まれる場所へ分散させる**」という判断を覆す側の主張になる。覆すには根拠が要るが、
その根拠になるはずの利用実績が無い（本番ユーザー5人・全員 admin、記録18件、
`ai_outputs` は開発時の動作確認のみ）。

なお NN/g の結論は「入口を1か所に集めるな」であって「実装を分けろ」ではないため、
**出口（窓）が1つで入口が複数**という形自体は第1段階の判断と矛盾しない。
「3つある」こと自体は問題ではなく、問題があるとすれば「どれを押しても同じ窓が開くのに
見分けがつかない」ことなので、論点は数ではなくラベルの差別化として立て直すべき。
