# 初回リリースを Free + Pro（IAP）同時で出し、課金軸を「肩代わりした手間」に置く

日付: 2026-09-05
状態: 決定（実装は未着手）

## 背景 / Why

`docs/decisions/20260823-pricing-plan-review.md` で、**課金軸を「機能」から何に移すかが未決のまま**止まっていた。
アグリハブの無料プランに「何人でも利用可能」「GAP管理」「病害虫診断」「帳票出力」が全部入っており、
機能の有無では課金理由が作れないと分かったためである。

その空欄に、オーナーの判断が入った。

> アプリを入れる、有料プランを契約したいと思う背景として、必ず「楽をしたい」という点がある。
> その楽を入れて農業の品質が向上するのであれば980円は安いと感じるはず。

## 決めたこと

### 1. 課金軸は「肩代わりした手間の量」

機能の数でも、蓄積データの活用範囲でもない。**楽になった量**で課金する。

この軸を採ると、Free と Pro の分け方が自動的に決まる：**機能は削らない。量で分ける。**
機能を削ると「アグリハブは無料でできる」と直接比較され、こちらが負ける。
量で分ければ、比較の土俵が「どれだけ任せられるか」に移る。

### 2. 初回リリースを Free + Pro 同時で出す

`docs/roadmap.md` の「実装順序の原則」は
**「マルチテナント化＋Stripe連携が未着手のためプラン強制はできない。機能は先にFree相当で全部作り、
アクセス判定は1箇所の共通関数を通す形にしておく」**としていた。**この順序を部分的に覆す。**

覆す範囲は **iOS の IAP による個人向け Pro だけ**。Team（Web契約・Stripe）は据え置きで、
マルチテナント化の完了を待つ。roadmap 自身が「個人向け（Free→Pro）はIAPで摩擦なく即決課金できることを
優先する」と既に決めているので、方向としては整合している。

**覆せる理由は、律速が変わらないから。** Apple Developer の登録（個人でも数日、Paid Applications 契約の
銀行・税務審査を含めるとさらに数日）が全体の律速で、**その待ち時間の中に IAP の実装が収まる**。
待ち時間を埋めるだけなので、同時リリースの追加コストは実質ゼロになる。

### 3. 撤退線を先に引く

**IAP の実装が Apple の登録完了に間に合わなかったら、Free のみで先に出す。**
課金を待って申請が遅れるのは本末転倒で、1ヶ月止まっている状態を長引かせるだけ。
この線を先に引いておかないと「もう少しで終わるから」で延び続ける。

### 4. Free の上限を当初設計より緩くする

| 機能 | 当初（roadmap 2026-07） | 新 | 緩める理由 |
|---|---|---|---|
| 記録に聞く | 1日3回 | **1日10回** | 言い回しを変えて聞き直すのが実際の使い方。3回では試行の途中で切れる |
| 写真で診断 | 1日1枚 | **1日3枚** | 1枚では「当たるかどうか」しか分からない。単価は最大なので3枚で止める |
| 次の散布はいつ？ | 1日1回 | **1日3回** | 圃場・作物ごとに聞くため、1回では1圃場で終わる |
| 作付けの相談 | （未設定） | **1日3回** | 新設。往復して詰める性質なので1回では会話にならない |
| 音声メモ | 1日5回 | **1日10回** | 記録習慣の核。単価が軽い（文字起こしは無料API）ので余裕を持たせる |

設計思想は roadmap のまま——**上限に達した瞬間＝価値を体験し切った瞬間**にアップグレード導線を置く。
ただし当初の値は**体験し切る前に切れる**水準だった。「体験は完了するが、日常使いには足りない」に置き直す。

**上限値は実測後に見直す。** `ai_outputs.cost_usd` に1呼び出しごとの原価が入っているので、
現場で使われ始めたら実際の原価と利用頻度を見て調整する。

### 5. 上限の判定はサーバー側で行う

`src/ui/aiFeatures.ts` / `expo-prototype/lib/ai.ts` の `canUseAiFeature()` は**表示制御のみ**に留める。
クライアントの数え上げは回避できるため、課金の判定根拠にはしない。

**判定は `api/_auth.ts`（全AI APIが既に通っている認証）に回数チェックを足す。**
カウントの真実の源は既存の `ai_outputs` テーブル（`organization_id, kind, created_at` の
インデックスが既にある）。**失敗した呼び出しは数えない**（保存は成功時のみ行われる）——
エラーで消費されるのは利用者に不利で、問い合わせの原因になる。

### 6. 「楽」を測るデータを、課金より先に取り始める

課金軸が「楽」である以上、**それを測っていないと値付けの根拠が無く、利用者にも示せない**。
今は測っていない。最小で意味のある2つだけ先に入れる。

| 何を足すか | どこに | 何が言えるようになるか |
|---|---|---|
| `reports.input_seconds` | フォームを開いてから保存までの秒数 | 1件あたりの入力時間。音声・コピー・手入力の比較 |
| `reports.source`（`manual` / `voice` / `copy` / `advice`） | 記録の作られ方 | AIが起点になった作業の割合 |

この2列で「1件あたり何秒短くなったか」「AIが起点の作業がどれだけあるか」が言える。
相談で出た「やること」が実際の作業記録と一致したかは、**既に `matchActions` で照合済み**
（`src/lib/adviceMatch.ts`）なので、新たな計測は要らない。

## 検討した代替案

- **v1.0 は Free のみ、v1.1 で IAP**（当初のこちらの推奨）→ 採らない。律速が Apple の登録待ちである以上、
  待ち時間に実装すれば同時リリースのコストはほぼゼロ。ただし**撤退線（3.）を引くことでこの案に退避できる**
- **Free を機能で削る**（診断は有料だけ等）→ 却下。競合の無料プランと直接比較され、機能表で負ける
- **課金軸を「蓄積データの活用範囲」にする**（20260823 の案）→ 見送り。データが貯まっていない現時点では
  Free と Pro の差が体感できず、課金理由にならない。将来 Team プランで再検討する
- **計測を課金の後にする** → 却下。課金軸の根拠そのものなので、後回しにすると値付けを説明できない

## 影響範囲

- **DB**: `reports` に2列追加（`input_seconds` / `source`）。どちらも NULL 許容で既存行に影響なし。
  RLS は行単位のポリシーなので列追加の影響を受けない。購読状態は `organizations.plan` が既にあるため
  新規テーブルは不要
- **既存機能**: 削除なし。上限に達した場合も機能自体は残り、翌日に戻る
- **ストア審査（増分）**:
  - **3.1.1** デジタル機能の課金は IAP 必須（Web で決済させると即リジェクト）
  - **3.1.2** サブスクの表示要件：価格・期間・自動更新の明示、**購入の復元ボタン**、
    利用規約とプライバシーポリシーへのリンク
  - **Paid Applications 契約**（銀行口座・税務フォーム）が別途必要。**Apple Developer 登録と同時に着手する**
  - `expo-in-app-purchases` は非推奨。`react-native-iap` か RevenueCat を使う（EAS Build 前提でよい）。
    レシート検証はサーバー側（`api/`）で行う
- **利用規約**: サブスクを出すなら必要。プライバシーポリシーとは別物で、現在は存在しない

## プレモータム（半年後に失敗していたとしたら）

1. **課金を待って申請がさらに遅れた。** 1ヶ月止まっていたものが3ヶ月になる。
   → **撤退線（3.）がこれへの唯一の防御**。守れなければこの決定自体が失敗になる
2. **「楽になった」を測ったが、実際には楽になっていなかった。** worker が0人のまま、
   測る対象が管理者しかいない状態が続く。→ 現場に配ることが計測の前提
3. **上限が緩すぎて原価が膨らんだ。** Free の利用者が増えるほど赤字が増える。
   → `ai_outputs.cost_usd` を月次で見る運用を決めておく。上限は後から締められる
4. **サブスクの表示要件を落としてリジェクトされた。** 復元ボタンや規約リンクは定番の指摘。
   → 実装時に 3.1.2 のチェックリストを先に作る

## 別件の発見：Guideline 5.1.1(v) アカウント削除

PM リファレンスの確認中に見つかった。**アプリ内にアカウント削除の導線が無い**
（`expo-prototype/` に該当コード0件。削除は Web の管理画面のみ）。

本アプリはアプリ内でアカウントを作れない（管理者が発行する）ため、規定の文面上は対象外と読めるが、
**審査で聞かれる頻度が高い項目**であり、`docs/app-store-submission.md` の対策表にも入っていない。

最小の対応は、設定画面に「アカウントの削除を依頼する」を置き、
`info@kishufarm.com` への問い合わせと「農場の管理者が発行・削除する」旨を明記すること。
実装は小さい。**申請前に入れる。**
