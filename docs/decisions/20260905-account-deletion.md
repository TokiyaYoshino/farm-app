# アプリ内アカウント削除を追加する

日付: 2026-09-05
状態: 実装
関連: `docs/pre-release-audit.md` の 4 と 7

## Why

App Store Guideline **5.1.1(v)** は「アカウント作成をサポートするアプリは、アプリ内で
アカウント削除もできなければならない」と定めている。現状の farm-app には削除導線が無く、
`public/privacy.html` の「申し出があった場合に削除します」という問い合わせ窓口のみ。
Apple は原則としてこれを認めないため、リジェクト要因になる。

本アプリは自由登録が無く管理者がアカウントを発行する方式なので、Apple の
「組織が構成員のアカウントを管理するアプリ」の例外を主張する余地はある。だが
審査担当が認めるかは運任せで、揉めると1往復（数日）を失う。実装したほうが早い。

あわせて、既存の管理者によるユーザー削除（`src/App.tsx`）が `users` 行を消すだけで
**Supabase Auth のユーザーを消していない**問題も同じ経路で直す。消したはずの人が
有効なJWTを取得でき、`api/_auth.ts` の `requireUser` を通って AI 系エンドポイント
（＝OpenAI キーを使う経路）を叩けてしまう。

## 仕様

新設する `POST /api/delete-account` が2つの経路を兼ねる。

- **本人による削除** — `user_id` 省略。ログイン中の自分を削除する
- **管理者による削除** — `user_id` 指定。同一組織の利用者に限る（他組織は 403）

削除するもの:
1. Supabase Auth のユーザー（先に消す。逆順だと孤児が残り、それが一番危ない状態）
2. `users` 行
3. `device_tokens` は `users(id) on delete cascade` で自動的に消えるため個別処理は不要

**ガード**: 対象が管理者で、かつ組織内の管理者が1人だけの場合は削除を拒否する（409）。
組織が管理不能になるため。

**作業記録は削除しない。** `reports` / `schedules` / `comments` は組織の記録として残す。
農薬の使用記録は出荷先対応・GAP の観点から作業者ごと残す必要があり、退職者の記録が
消えると防除履歴が欠落する。削除確認画面にこの旨を明記する（審査でも運用でも説明がつく）。

## 検討したが採用しなかった案

**匿名化して `users` 行を残す**（氏名・ログインID・auth_id を消して行は残す）。
記録画面での作業者名の表示が壊れないという利点があるが、
- 現行の管理者削除が既に行ごと消す挙動で、それで運用できている
- 行を残すと利用者一覧から隠すためのフラグ列が要り、マイグレーションが増える

今回は既存挙動を変えない範囲に留める。**ただし記録に残る `user_id` は
users 行が消えると名前解決できなくなる**（現行も同じ）。GAP 対応で作業者名の
保持が必要になった時点で匿名化方式への移行を再検討する。**未解決事項として残す。**

## 影響範囲

- DB スキーマ変更なし
- RLS への影響なし（削除は service_role 経由。RLS 適用の前後どちらでも動く）
- 既存機能の削除なし。管理者の削除操作は導線そのままで、内部の呼び先が
  クライアント直の `supabase.from("users").delete()` から API 経由に変わる
- プライバシーポリシーの「アカウント削除の申し出があった場合」という記述は、
  アプリ内導線ができたことに合わせて更新が必要（監査 5 の対応時にまとめて行う）
