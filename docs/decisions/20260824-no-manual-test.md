# 無マニュアルテストと「説明を書く前に、書かずに済ませる方法を考える」

- 日付: 2026-08-24
- 状態: 採用（運用ルール）
- 種別: 仕様変更（プロダクト全体の判断基準）

## 課題（Why）

機能はどれも競合レビュー調査に裏付けられて作ったのに、使われている実感がない。原因を追うと、機能の有無ではなく**置き場所と言葉**だった。

決定的な例が作物名マッピングで、**説明文を76文字書いた結果、本番の作付けは7件すべて未設定＝機能が完全に死んだ**（`20260824-plain-language-and-crop-mapping.md`）。正解は説明を短くすることではなく、自動で当てて聞かないことだった。

同じ病気が他にもある。AI機能を横スクロールの先に置いてラベルで説明しようとしていた件（`20260823-ai-information-architecture.md`）も、原因は同じ「システムの都合をそのまま画面に出している」。

## 決めたこと

### 目指す状態

> **説明書を読まずに始められて、必要になった瞬間にその場で分かる。**

事前に読ませるマニュアルはゼロを目指す。ただし詰まりうる箇所には**文脈内の一行**を置いてよい（「南高梅なら『うめ』」のような例示）。これは説明書ではなくUIの一部。

### 手当ての優先順（上ほど強い）

1. **そもそも聞かない** — 自動で決める
2. **初期値・例示で埋める** — プレースホルダ、入力例、前回値の引き継ぎ
3. **空状態に一行置く** — データが0件の画面に「ここに○○が並びます」。初回にだけ効くので邪魔にならない
4. **`?` を置く** — タップで1〜2文。**上の3つが使えないときの最後の手段**

`?` の使い方:
- **中身が3文を超えたら設計を疑う。** 説明が長くなるのは、UIが説明を要求している証拠
- **押されない前提で設計する。** 押さなくても操作は完了できる状態にし、`?` は「なぜこれが必要か」を補う役割に留める
- **毎日触る導線に `?` が必要になったら、それは直す対象**

### 運用ルール（これだけは守る）

> **ヘルプ文言を書きたくなったら、まず「書かずに済ませる方法」を先に検討する。**

説明を足すのではなく、説明が要らない形に変えられないかを1回考える。それでも無理なら書いてよい。

### テストのやり方

農家に**何も説明せず**アプリを渡し、タスクを口頭で言うだけ。横で黙って見る。**助けない**（質問されたら「どう思いますか？」と返す）。詰まった箇所がそのまま課題リストになる。

| # | タスク | 扱い |
|---|---|---|
| 1 | 自分の畑を1つ登録する | **必達** |
| 2 | 今日やった作業を1件記録する | **必達** |
| 3 | 農薬を撒いたことを記録する | **必達** |
| 4 | 「去年いつ○○を撒いたか」を調べる | 記録して次で直す |
| 5 | 提出用の帳票を出す | 記録して次で直す |

必達3つは毎日使う主導線で、ここで詰まると定着しない。**説明ゼロで完了できること**を目指す。

### これは門番ではない

**詰まりポイントを可視化する診断**であって、合否を出すものではない。

- 残り2つで詰まっても**機能をローンチから外さない。導線も下げない。そのまま出す**
- 手当てが間に合わなければ**既知課題として記録し、ローンチ後に直す**
- **完璧を待たずに出す**

## 検討した代替案

- **チュートリアル・初回ガイドを作る** → 却下。読まれない前提のものを作るコストを、聞かずに済ませる設計に回すほうが効く
- **ヘルプページを整備する** → 却下（優先度として）。ヘルプが要る時点でUIが説明を要求しており、原因を残したまま対症療法になる
- **テストで合否を出して、落ちた機能を外す** → 却下。ユーザーの需要はレビュー調査で裏付けられており、詰まりは置き場所の問題。機能を削ると需要ごと捨てることになる（CLAUDE.md の「既存機能を削除しない」とも整合）

## 影響範囲

- **DB / 権限**: なし
- **既存機能**: なし（判断基準であり、個別の実装変更は各決定ログで扱う）
- **今後の実装すべて**: 新しい画面・項目を作るとき、この優先順で設計する

## プレモータム（半年後に失敗していたとしたら、何が起きたか）

1. **テストを一度もやらなかった。** 現場の作業者（worker）が0人のままで、渡す相手がいなかった。→ **これが最も起こりうる**。テストの前提はアカウントを作って現場に渡すことで、それ自体が未着手のまま残っている
2. **「自動で決める」を優先しすぎて、誤った自動判定が起きた。** 聞かないことを優先するあまり、推測で当てにいった。→ 作物名マッピングでは「確実な2つだけ当てる」に絞ったが、次の機能で同じ規律を保てるとは限らない
3. **ルールが形骸化した。** 「書かずに済ませる方法を考える」が儀式になり、実際は考えずに書いた。→ 決定ログに「何を書かずに済ませたか」を残すことでしか担保できない

## 要ユーザー対応

**現場の作業者アカウントを作って渡すこと。** 本番のユーザー5人は全員 admin で worker は0人のため、無マニュアルテストを実施する相手がいない。テストの前提条件がまだ揃っていない（`docs/handoff-input-redesign.md` でも最優先の未着手として記録されている）。
