# 作物ごとの相談（農業エージェント）

- 日付: 2026-08-10
- 状態: 決定
- 種別: 機能追加

> **2026-08-10 改訂**: 当初は「ボタンを押すと助言カードが1枚出る」一発物として実装したが、それでは
> エージェントにならない（会話にならず、作物ごとに溜まらず、言ったことの実施を追えない）。
> **会話・蓄積・記録との照合**の3点を満たす形に作り直した。情報源の3層分離と法令上の安全側の
> 倒し方（下記）は変更していない。

## 背景（Why）

競合レビュー89件の調査（`docs/research/competitor-app-reviews-2026-08.md`）で、**「次にやる作業・データが分からない」への支援が farm-app に無い**ことが分かった（`competitor-gap-analysis-2026-08.md` ①）。コード検索でも該当機能のヒットは0件。

この課題は**記録の検索では解けない**。既存の `api/search-chat.ts` は「渡された作業記録のみを根拠に」「書かれていない情報は推測せず『記録からは分かりません』と答える」という厳格な検索専用で、これは意図した設計であって欠陥ではない（記録に無い数字をAIが作ると帳簿として使えなくなる）。

しかし本番の実データは **n=18件・4.5か月**（`docs/handoff-input-redesign.md` 2章）。記録が薄い農場では検索チャットは何も返せない。**必要なのは記録の検索ではなく知識の補填**である。

## 決定

**作付けごとの相談スレッドを作る。** 「キャベツこれどうしたらいい？」と聞くと LLM が答え、
やりとりが**その作付けに溜まり**、助言した作業は**作業記録と照合される**。

材料は作物名＋作付日＋気象。作業の段取りは LLM の一般知識で出すが、**農薬に関する数値は LLM に
生成させず、農薬登録情報（FAMIC 登録適用部）の原文を機械的に渡す。**

新設: `api/advise.ts`（既存 `search-chat.ts` は改造しない）。

### エージェントとして成立させる3条件

| # | 条件 | 実現 |
|---|---|---|
| 1 | **会話**として続く | `messages`（これまでのやりとり）を渡す。直近12件までをプロンプトに載せ、切ったら `limits` に件数を出す |
| 2 | **作物ごとに溜まる** | `crop_advice_messages` / `crop_advice_actions`（`scripts/migrations/2026-08-10-crop-advisor.sql`）。作付けを開くと前の相談が残っている |
| 3 | **記録と照合できる** | 助言から「やること」を構造化し、`work_type` をキーに `reports` と突き合わせる（`lib/adviceMatch.ts`） |

3が要点。**言ったことの実施を追えなければ、単なるチャットであってエージェントではない。**

### 照合の設計（`lib/adviceMatch.ts`）

- **照合結果を保存しない。** 毎回計算する。作業記録は後から追加・修正されるので、「実施済み」を
  DB に書くと実態とずれる（`lib/pesticideUsage.ts` / `lib/metrics.ts` と同じ方針）
- **判定は4値。** `done` / `pending` / `overdue` / **`unmatchable`**。`work_type` を作業記録の語彙に
  落とせなかった助言は `unmatchable` であって `pending`（未実施）ではない。
  **混ぜると「やったのに未実施と言われる」か「できていないのに見逃す」のどちらかが起きる。**
  画面でも「記録と照合できません」と出し、警告色を使わない
- **`work_type` は語彙の完全一致だけを通す。** API 側で語彙外の値は `null` に落とす。
  近いものを当てはめると「やっていないのに実施済み」になる。落としたことは `limits` に出す
- **期限が無い助言は期限切れにしない。** LLM の「今週中」を日付に落とせなかっただけで催促するのは誤り
- **照合期間は助言が出た日から。** それ以前の作業は「言われる前にやった」ので数えない。
  終わりは切らない（期限後にやった記録も拾う）
- **圃場は見ない。** 助言は作付け単位で圃場を指定していないため（絞ると別圃場の作業を見落とす）
- 「やらない」判断（`dismissed_at`）は行を消さずに立てる。判断の履歴になる

### 情報源を3層に分け、混ぜない

| 層 | 内容 | 出所 | 扱い |
|---|---|---|---|
| 1 | 作物名・作付けからの経過日数・今日の日付・地域 | 呼び出し側が渡す事実 | プロンプトに事実として渡す |
| 2 | 希釈倍数・使用時期・本剤の使用回数・総使用回数・使用方法 | **FAMIC 登録適用部の原文** | LLM に生成させない。プロンプトには原文を渡し引用のみ許す。**レスポンスでも `registrationFacts` として別に返し、画面はそちらを表示する** |
| 3 | 作業の段取り・生育段階・時期の目安 | LLM（gpt-4o-mini）の一般知識 | 「目安」と明示。公的な栽培基準ではない |

層2を配列で別に返すのが要点。**LLM の文章に混ざった数字を利用者に信じさせない**ため、画面には原文の表を出す。

### 検討した他の案

| 案 | 内容 | 判断 |
|---|---|---|
| A | 記録から次の作業を推定（既存 `search-chat.ts` の拡張） | **却下**。n=18 では推定材料が無い。かつ「記録のみを根拠に」の設計を崩す |
| A' | 既存の `SearchChatSheet` に相乗りする | **却下**。あちらは全記録を横断する検索で作付けに紐付かないため、作物ごとに溜まらない。目的（記録の検索 / 知識の補填）も逆 |
| B | 公的な栽培暦データを取り込む | **保留**。JA全農ちば統一栽培暦（44作物・作型×月旬×作業名）は構造的に理想だが、**果樹を含まないため本番の ぶどう・にんにく が対象外**。WAGRI は ¥40,000/月かつ栽培暦カテゴリが無い。カバー率が出ないうちは採らない |
| **C** | **LLM の一般知識 ＋ 気象 ＋ 作付日。農薬は FAMIC 原文** | **採用**。追加コストゼロ・全作物で成立し、法令に関わる数値だけを公的原文に寄せられる |

B は将来 C の上に重ねられる（層3を栽培暦に差し替える）。C を先に出しても手戻りにならない。

## 法令上の安全側の倒し方（`20260805-pesticide-precheck.md` の非対称性を継承）

- **FAMIC が `-` を返す欄は「記載なし（判定不可）」**。「制限なし」ではない。登録4407（ｻﾝｹｲ園芸ﾎﾞﾙﾄﾞｰ / ぶどう）は使用時期・使用回数・総使用回数がすべて `-` で実在する。ここを取り違えると使用者を法令違反に導く
- **`famic_crop_name` が未設定なら適用行を1件も渡さない**（`toFacts` が空配列を返す）。紐付けの無い状態で全行を渡すと、他作物の適用情報をこの作付けのものとして提示してしまう。`lib/pesticideUsage.ts` の `no_famic_crop_name` → 判定不可 と同じ扱い
- 作物名の突き合わせは**完全一致のみ**（部分一致は「うめ」が「うめ以外の…」に当たる）
- プロンプトで禁じていること: 渡されていない農薬値の推測・補完、範囲外の農薬/作物/病害虫の使用可否、**新たな農薬名の推薦**（登録の有無を確認できないため）、肥料・農薬の施用量の数値断定
- **出典と限界は LLM に書かせず、サーバー側で固定文言を返す**（`sources` / `limits`）。「どこまでが公的な情報でどこからが AI の一般知識か」を利用者が区別できないと、目安を規制値のように受け取る
- **打ち切りを黙って行わない**。適用行は30件・やりとりは12件まで参照し、切ったぶんは `limits` に件数を明記する（黙って削ると「載っていない＝適用が無い」「前に言ったのに覚えていない」と受け取られる）
- **`unmatchable` を未実施と決めつけさせない**。プロンプトに「『記録と照合できません』は未実施を意味しない」を入れ、画面でも同じ文言を出す

## 前提（列追加は完了・紐付けが未実施）

`crops.famic_crop_name` 列は **2026-08-10 に本番へ適用済み**。ただし**7件すべて `null`＝未紐付け**。

紐付けが済むまで層2（農薬の注意事項）は**常に空**になる。層1・層3（作業の段取り）は動くので機能自体は成立し、`limits` に「紐付いていないため薬剤の使用可否は判断していない」と出る。**壊れるのではなく、判定不可として縮退する。**

同じ理由で、**既存の農薬使用回数チェック（`PesticideUsageCard`）も紐付けが済むまで全件「判定不可」**。

紐付けの表と手順は `docs/handoff-input-redesign.md` 12章。FAMIC 登録適用部を登録番号ごとに引いて表記を確認済み（本番7件はすべて品種名を含まない一般名で、南高梅型の曖昧さは無い）。**本番データの更新なので実行には承認が必要。**
