# Web版のリリースと切り戻しの設計

- 日付: 2026-09-09
- 状態: 採用（実装済み。本番反映は未）
- 種別: リリース運用＋安全側の実装

## 課題（Why）

このブランチの変更（相談スレッド・入力3択・文言/記号の整理・空状態CTA・entry_point）を本番Web版に出し、**同じ農場の作業者に試してもらう**。出す前に公開可否を調べたところ、**私の一存で進めてはいけないものが2つ**出た。

| # | 内容 | 判断 |
|---|---|---|
| 1 | **AIの日次上限が1行も実装されていない。** `api/_auth.ts` 自身が「Free枠の日次上限は設計があるだけで未実装なので、**支出の歯止めが無い**」と書いている | **今回塞ぐ** |
| 2 | **RLS が `allow_all` のまま。** anon キーはバンドルに焼き込まれるので、URLを知る第三者が curl で全データを読める | **今回は塞がない**（下記） |

あわせて、移行SQLとデプロイの**順序ミスが事故になる**構造があった。先にコードが出ると `advice_threads` が無く相談タブが全滅し、`ai_outputs.entry_point` に至っては**列が無いと監査ログが黙って落ち続ける**（`saveAiOutput` は `console.error` するだけで画面に出さない）。

## 決めたこと

### 1. 順序のハザードを、人間の注意力ではなくコードで消す

起動時に `advice_threads` の存在を確かめ、**無ければ相談タブごと出さない**（`threadsReady`）。

- テーブルが無いエラー（`42P01` / `PGRST205` / スキーマキャッシュ）**だけ**を「未適用」と判定する。通信や権限の一時的な失敗では消さない（一時的な不調で機能ごと消えるほうが困る）
- 未適用のときはナビから「相談」を外し、`tab === "advice"` に居座らないようホームへ戻し、**ホームの「作付け中 — 相談できます」カードも出さない**（押しても空振りするため）
- **SQLを流す前にデプロイしても、以前と同じ画面が出るだけ**になる。流した後は次のリロードで自動的に現れる（デプロイ不要）

### 2. AIの日次上限（`checkDailyLimit`）

`api/_auth.ts` に追加し、AI系5本（診断・相談・日報・防除助言・音声整理）の `requireUser` 直後に掛けた。

- `ai_outputs` を service role で `created_by` × `created_at >= 今日` で数える。**日付の境目は日本時間で切る**
- 上限は **画像診断 20回/日、その他 50回/日**。`docs/roadmap.md` の Free枠設計（1〜5回）とは目的が違う。**あちらは課金の線引き、こちらは暴走を止めるだけ**なので、運用を邪魔しない広さにした
- **fail-open。** 数える側が失敗したら通す。数える処理の不調でAI機能が全滅するほうが、上限を1日すり抜けるより損害が大きい
- **`search-chat` だけ上限の外。** `ai_outputs` への保存実装が無く数えられないため。テキストのみで単価が最も低いので、それを承知で残す

### 3. RLS は今回適用しない（理由を明示して残す）

`allow_all` のままで出す。理由:

- **今の本番と危険度が変わらない。** これは今回のデプロイが新たに作る穴ではなく、2026-08-28 のリリース時点から続いている状態
- 試すのは**同一組織の作業者**。同じ組織のデータが見えるのは元々の設計どおりで、越境は起きない（別組織のデータが本番にまだ無い）
- 適用は「本体SQL＋crop-advice＋`advice_threads`」の**3系統**が要り、Auth Hook の有効化（ダッシュボード操作）と越境テストまで含む別作業

**ただし増えるものはある。** 相談スレッドに会話全文が入るので、**anon キー経由で読める情報の種類が増える**。

**別の農家に配る前には必須。** `docs/rls-rollout.md` の手順を実行し、`advice_threads` のポリシーも忘れずに作ること（新規テーブルなので `allow_all` で作られる）。

## 切り戻し（Vercel の即時ロールバックのみ）

**コードは戻せる。DBは戻さなくてよい。** 追加した列はすべて nullable で、古いコードは無視する。

**副作用が1つある。** 新コードが書いた `crop_id = null` の行は、古いコードの一覧（`.eq("crop_id", cropId)`）から**消える**。該当は「作付けに紐づかない主題スレッドの会話」と「**道具の結果メッセージ全部**」（`appendToolMessage` は `crop_id: null` を固定で入れる）。

データは残っており、再デプロイすれば戻る。**不可逆な損失ではない。** ただし切り戻し中に古いコードで書かれた会話は `thread_id = null` になり、再前進したとき今度はスレッド一覧から消える（移行SQLは一度きりの実行）。**往復すると両方向に穴が空く。**

## プレモータム

1. **上限が緩すぎて意味がなかった。** 20/50回は暴走の下限を切っているだけで、1人が1日20回の画像診断を回せば普通にコストは出る。→ 実際の利用を見て締める前提
2. **fail-open が常時 open になっていた。** service role の設定ミス等で `checkDailyLimit` が毎回 null を返しても、**画面には何も出ない**ので気づけない。→ 本番デプロイ後に1回だけ意図的に上限を超えて 429 を確認する
3. **`threadsReady` が誤検知して相談タブが消えた。** エラーコードの判定を誤ると、テーブルがあるのに機能が出ない。→ 判定はテーブル不在系のコードに限定してあるが、初回リリース後に実際に相談タブが出ることを必ず確認する

## 検証

`npx tsc --noEmit` clean / `npm run build` 成功。デモで `threadsReady = false` を強制し、**ナビが「ホーム / カレンダー / 分析 / メニュー」になり、ホームの作付けカードも消え、他の画面が壊れないこと**を確認した（ページエラー0件）。

**未検証**: 日次上限の 429（サーバー側なのでローカルでは動かせない）。**本番デプロイ後に1回だけ実際に叩いて確認する。**
