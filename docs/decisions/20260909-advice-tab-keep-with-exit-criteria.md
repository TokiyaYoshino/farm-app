# 相談タブは維持する。ただし撤退条件を先に決める

- 日付: 2026-09-09
- 状態: 採用
- 種別: 仕様判断（情報設計）＋計測の追加
- 根拠: [`docs/research/ai-tab-evidence-2026-09.md`](../research/ai-tab-evidence-2026-09.md)、[`docs/research/dl-target-20k-2026-09.md`](../research/dl-target-20k-2026-09.md)

## 課題（Why）

相談タブ（AIとの会話を主題ごとのスレッドに溜める）をボトムナビに置いた判断が妥当かを、外部事例で検証した。**結果は、この判断にとって不利なものが多く出た。**

1. **Amazon Rufus** はボトムナビのAIチャットタブで **3億人・MAU +149%・付随売上 約120億ドル** を出しながら、**2026-05 にタブという形をやめて検索バーに埋め直した**。理由は「別のチャットを開く摩擦がDAUを削いだ」（**二次情報**）
2. **国内でボトムナビにAI/相談タブを置いた例は1件も確認できなかった**（取得できた範囲。LINEヤフーの Agent i ですら「各タブ**から**アクセス」）
3. **構造が最も近いあすけん**は、相談チャットを **β・iOS先行・プレミアム限定・月10回上限**という最も絞った形で出し、**主要導線に置いているのは入力系AI**（「＋」の直下に2か所常設）
4. **Snapchat My AI**（評価 3.05→1.67、1★ 35%→75%）と **WhatsApp Meta AI**（消せない青い円）が炎上した主因は、AIの質ではなく**消せない一等地の占有**
5. あすけんのプレミアム解約者は「**Geminiの方が画像解析が正確だった**」と書き、あすけん自身は**AIコスト増を理由に値上げ**している

## 決めたこと: 維持する。ただし撤退条件と計測を先に置く

**外部事例は「やめろ」と言っているが、それでも維持する。** 理由を順に書く。

1. **この設計の起点は、外部調査ではなくオーナー自身の実利用フィードバック**（「AIの入口が多すぎて使いにくい。普段AIを使っている自分ですら」）。このセッションでは一貫して「実際に触って出た事実 > 他社を調べた事実」で判断してきた。ここだけ基準を変えない
2. **撤退が安い。** ナビから外すのは `navItems` の1行で、`CLAUDE.md` の規約どおりタブの中身は残せる。高い可逆性がある判断は、先に試して измерするほうが速い
3. **Amazon の理由付けが二次情報。** 反対論の最大の柱が一次表明として確認できていない
4. **代替案（履歴の書庫に降格）は、元の問題を再発させる。** 「どこにあるか分からない」がまさにオーナーの不満だった

ただし外部事例は無視しない。**「維持する」ではなく「測って、駄目なら降ろす」**にする。

### 撤退条件（先に決めておく）

移行SQL適用後、**worker を含む実利用が始まってから30日**を1期として測る。

| 条件 | 判定 |
|---|---|
| `entry_point` が `thread` / `thread_tool` の呼び出しが、AI呼び出し全体の **20%未満** | **相談タブをナビから降ろす**（中身はホームの履歴行から到達させる。機能は消さない） |
| かつ 相談スレッドの新規作成が **月1件未満** | スレッド自体をホームの履歴に降格 |
| `thread` / `thread_tool` が **40%超** | 維持を確定し、以後この撤退条件は適用しない |
| 20〜40% | もう1期（30日）延長して再判定 |

**バッジは「タブの引きが足りない」ことの補助動力なので、判定はバッジ有りの状態で行う。** バッジがあっても20%に届かないなら、形が合っていない。

### 撤退条件を測れるようにする（今回の実装）

3回続けて情報設計を変えて3回とも「効果は未検証」で終わっている。母数の少なさだけでなく、**そもそもどの入口から使われたかを記録していなかった**のが原因。

- `ai_outputs.entry_point` を追加（`scripts/migrations/2026-09-09-ai-outputs-entry-point.sql`）
- `saveAiOutput` の payload で **`entryPoint` を必須**にした。任意にすると導線を足したときに書き忘れ、「使われていない」と読めて集計が嘘になる
- **`kind` では代用できない。** 例えば `kind='diagnosis'` は（記録一覧の写真直下／記録詳細／＋記録の3択／相談タブの道具）の4か所から出る
- 値: `thread` / `thread_tool` / `quick_picker` / `note_field` / `home` / `record_list` / `calendar` / `report_photo` / `report_detail`

集計は SQL 1本で出る（マイグレーションのコメントに例を書いた）。

## 外部事例のうち、今すぐ効かせたもの

- **汎用LLMとの比較負け対策**: 相談の空状態と新規作成シートで「**その作付けの記録と農薬の登録内容もふまえて答える**」ことを明示済み。ChatGPT / Gemini にできないのはここだけなので、画面で言う
- **「勝手に出てくる」方向**: 89件のレビュー実測で唯一の年齢言及（20代新規就農）が求めたのは「相談しに行く」ではなく「教えてくれる」形。Duolingo の Explain My Answer が65%使われたのも**間違えた直後の画面に置かれたから**。ホームの「今日の一手」「作付け中のやること」がこの形にあたる。**今後AIを足すときは、タブの中ではなくこちらに置く**

## 影響範囲

- **DB**: `ai_outputs.entry_point` を追加（nullable なので既存行に影響なし）
- **API**: なし
- **既存機能**: 削除なし。挙動の変更もなし（記録する列が1つ増えただけ）
- **注意**: **マイグレーション適用前にデプロイすると `ai_outputs` の insert が失敗する。** 失敗しても画面は壊れない（`saveAiOutput` はエラーを握って握りつぶす設計）が、監査ログが落ちる

## プレモータム

1. **撤退条件を決めたのに、判定する日が来ない。** 本番の worker が0人のままなら30日が始まらない。→ **これが最大のリスク。** 使う人を増やすことが、どのUI改善よりも先
2. **20%という閾値の根拠が薄い。** 他社の同種の指標を取得できなかったため、直感で置いた数字。1期目のデータを見て閾値自体を見直す前提にする
3. **entry_point を足したが集計する画面が無い。** SQL を手で叩く運用になる。分析タブに出すのは、データが溜まってからでよい
