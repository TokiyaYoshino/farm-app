# AI出力は「結論を常時・前提は折りたたむ」、注意書きと集計はサーバー側で固定する

- 日付: 2026-08-29
- 状態: 採用
- 種別: 仕様変更（AI出力の構造・表示）

## 課題（Why）

「AI機能の出力が文章の塊で出てくる」という相談から。改修前に**実際に OpenAI を叩いて現物を測った**（本番のプロンプト・スキーマそのまま / gpt-4o-mini / 南高梅19件の記録・Open-Meteo の実データ）。体感と実態はかなりずれていた。

| 機能 | 画面に出る文字量 | 実際の問題 |
|---|---|---|
| 日報 | 181字 | **長さは問題なし**。`summary` の「作業は順調に進みました」が記録に無い評価で中身も無い |
| 防除助言 | 302字 | `avoidDays` が「降水確率98%で雨が予想され、薬効が流れる可能性が高いから」を**ほぼ同文で3日ぶん**並べていた |
| 作付けの相談 | 253字 | **本文74字に対して注釈179字**。注釈が本文の2.4倍で、しかもほぼ固定文言なので会話が続くほど同じ文で埋まる |
| 記録検索チャット | 129字 | 短いが**答えが間違っていた**。2026年の防除を「2025年に4回」と回答（正しくは1回） |

つまり「長い」が主症状に見えていたのは相談の注釈で、それ以外は長さ以外の問題だった。

### 記録検索の誤りの構造

同じ回答の中で、農薬の残り回数（「あと2回使えます」）は**正しかった**。この数字は `formatPesticideUsageForPrompt` が事前計算して渡しているもので、LLM は言い換えただけだったため。一方、間違えた防除回数は19件の記録から LLM に数えさせていた。

さらに `today` を渡していなかったため、「去年」を西暦に読み替える基準が無かった。

## 決めたこと

### 1. 数えるのはコード、言い換えるのが LLM

回数・集計を LLM に生成させない。`src/lib/metrics.ts` に `formatWorkCountsForPrompt`（年×作業種別の件数）を追加し、事前に数えた表を渡して「この表の数字をそのまま使い、数え直すな」と縛る。農薬の使用回数（`pesticideUsage.ts`）と農薬の適用情報（`advise.ts` の `registrationFacts`）が既に取っていた方針を、作業回数にも広げた。

あわせて `today` を渡し、「去年＝YYYY年」を明示する。

### 2. 根拠は渡した材料に実在するものだけ通す

`search-chat` の `evidence[].date` は、渡した記録テキストに実在する日付だけを通す。実在しない日付を根拠として出すと、利用者は確かめたつもりで確かめられない。落としたぶんは黙って消さず `notes` に件数を出す。

`advise.ts` が `work_type` を語彙の完全一致だけ通し、`due_from` / `due_to` を日付の形だけ通しているのと同じ扱い —— **スキーマが守るのは形、コードが守るのは意味**。

### 3. 注意書き・免責は LLM に書かせず、サーバー側の固定文言で返す

`search-chat` の system プロンプトにあった「総使用回数の原文には条件が含まれる」「混合剤は成分別に数える必要がある」は、毎回本文に混ざって長くなるうえ、書かれたり書かれなかったりしていた。`advise.ts` の `sources` / `limits` と同じく `notes` として分けて返し、プロンプトからは「注意書きは生成しないこと」と明示して外す。

**消すのではなく分ける。** どこまでが公的な情報でどこからが AI の一般知識かを利用者が区別できなくなるため、注意書き自体は必ず付ける。

### 4. 結論は常時・前提は折りたたむ

`src/ui/Disclosure.tsx` を追加し、次の方針で統一する。

| 常時表示 | 折りたたむ |
|---|---|
| 結論（`answer` / `reply` / `headline`） | 出典・限界・判断できないこと（`sources` / `limits` / `unknowns`） |
| 見ておくこと（`watch_points`、最大3件） | 注意書き（`notes`） |
| 根拠にした記録（最大3件） | 4件目以降の根拠・登録内容 |

開閉は部品の内部 state で持つ。呼び出し側に `useState` を作らせない（同じ画面に複数置くたびに state が増えるのを避ける）。

### 5. 捨てていた出力を出す

`advise.ts` は `watch_points` / `unknowns` を生成していたが、`crop_advice_messages` に保存先が無く**画面に一度も出ていなかった**。生成コストだけ払って捨てていたので、列を追加して表示する（`scripts/migrations/2026-08-29-crop-advice-watch-unknowns.sql`）。既存行は null になるため画面は null 安全に描く。

## 検討した代替案

### 一律に字数上限と max_tokens を下げる

最初の案だったが、実測でほぼ全否定された。日報は既に181字で削る余地が無く、防除助言も `headline` は14字で十分短かった。長さを一律に削ると、相談の注釈（安全上の情報）を削るか、根拠の記述を削るかになり、どちらも危ない。**問題は総量ではなく配分**だったので、折りたたみで配分を変える方に倒した。

### 記録検索の集計を全部クライアントで計算して LLM を通さない

「防除は何回」だけなら可能だが、自然言語の質問はもっと多様で（「カメムシが出たのはいつ？」等）、全パターンを事前計算はできない。**数字だけを事前計算して渡し、言い換えは LLM に任せる**中間に落とした。

### 画像診断も同時に詰める

実データに写真が1件も無く実測できなかった。測らずに `max_tokens` を下げると鑑別の根拠が途中で切れる恐れがあるため、今回は触っていない。写真が溜まったら測って判断する。
