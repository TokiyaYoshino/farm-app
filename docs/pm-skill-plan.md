# PMスキル作成プラン

作成日: 2026-07-19 / 対象: farm-app（紀州農場アプリ）

## 1. 背景と目的

farm-app は思いつきベースで仕様変更が発生しており、以下のリスクがある。

- 仕様の一貫性が崩れ、AppStore 公開（審査・リリース計画）の障害になる
- 変更の「なぜ」が記録されず、後から判断の根拠を追えない
- ロードマップ（docs/roadmap.md）と実際の開発が乖離する

そこで **Claude が PM として振る舞うためのスキル**を作る。オーナー（吉野）に PM 知見がなくても、機能提案・仕様変更・リリース準備の場面で Claude が PM のプロセスを回してくれる状態がゴール。

## 2. スキルがカバーする3領域

| 領域 | 内容 |
|---|---|
| PMの仕事の進め方 | 仕様変更の受け止め方（Why の深掘り→影響範囲→優先順位付け→記録）、ミニPRD 作成、RICE/MoSCoW 等の優先順位付け、スコープ管理、意思決定ログ |
| 周辺知識 | AppStore 審査ガイドライン・公開準備（プライバシーポリシー、審査リジェクト典型例）、リリース管理・バージョニング、React Native/Expo 移行時の留意点（ロードマップの方向性に合わせる） |
| ドメイン知識（農業） | 農薬管理（希釈倍数・使用基準・農薬取締法）、防除記録・作業日誌の実務、圃場・作付けの概念、GAP 認証など記録が資産になる文脈、農家ユーザーの利用実態（屋外・片手・短時間入力） |

## 3. スキルの設計方針

### 置き場所と構成

リポジトリ内 `.claude/skills/pm/` に置く（farm-app 専用の文脈を含むため、プロジェクトスコープが適切）。1スキル + 参照ファイル構成（progressive disclosure）：

```
.claude/skills/pm/
├── SKILL.md                  # トリガー条件 + PMとしての基本動作（500行以内）
└── references/
    ├── workflow.md           # 仕様変更フロー・ミニPRDの書き方・優先順位付け手法
    ├── templates.md          # ミニPRD / 変更提案 / リリースチェックリストのテンプレ
    ├── appstore.md           # AppStore公開の要件・審査対策・リリース手順の知識
    ├── agriculture.md        # 農業ドメイン知識（農薬・防除記録・圃場・GAP）
    └── product-context.md    # farm-app固有：ビジョン、ユーザー像、ロードマップとの整合ルール
```

### スキルの中核動作（SKILL.md に書くこと）

ユーザーが「○○機能を追加したい」「ここの仕様を変えたい」と言ったとき、いきなり実装せず PM プロセスを挟む：

1. **Why の確認** — 誰のどの課題を解くのか、既存機能で代替できないかを1〜2問で確認
2. **整合チェック** — docs/roadmap.md のフェーズ設計・方針（「使い続けてもらえるアプリが最優先」等）と照合し、ズレていれば指摘
3. **影響範囲の評価** — DB スキーマ・RLS・既存機能・AppStore 審査への影響を列挙
4. **ミニPRD の記録** — `docs/decisions/` に軽量な意思決定ログ（1件=数十行）を残してから実装に入る
5. **ロードマップ更新** — 採用した変更は roadmap.md に反映する

ポイント：**重厚な PRD 文化を持ち込まない**。個人開発のスピード感を殺さない「数分で書ける記録」を徹底する。

### トリガー設計（description）

発動すべき場面：新機能の提案、仕様変更の相談、優先順位の相談、リリース/AppStore 公開の話題、「これ作るべき？」系の相談。
発動すべきでない場面：純粋なバグ修正、リファクタ、デザイン調整（既存仕様の範囲内の作業）。

## 4. 作成の進め方（skill-creator のループに沿う）

### フェーズ1: 要件確定（〜0.5日）
下記のオープンクエスチョンを確定（各項目にデフォルト案あり、そのまま採用でも進められる）。

### フェーズ2: ドラフト作成（〜1日）
- SKILL.md + references 5ファイルを執筆
- agriculture.md と appstore.md は Web リサーチで裏取り（農薬取締法の記録義務、App Review Guidelines の最新版）
- product-context.md は既存 docs（roadmap / db-schema / CLAUDE.md）から抽出

### フェーズ3: テストと評価（〜1日）
現実的なテストプロンプトでスキルあり/なしを比較し、eval viewer でレビュー：

1. 「収穫予測をAIでやる機能を今すぐ入れたい」→ ロードマップ長期フェーズとの整合指摘 + ミニPRD が出るか
2. 「作業報告の入力項目を変えたい（土壌pHを必須にする）」→ 影響範囲（DB・既存データ・UX）の評価が出るか
3. 「AppStoreに出すには何が必要？」→ 具体的なチェックリスト（プライバシーポリシー、審査対策、Expo化の前提）が出るか

### フェーズ4: 改善ループ
フィードバックを基に書き直し → 再テスト。満足したら description 最適化（トリガー精度の自動チューニング）を実行。

### フェーズ5: 導入
`.claude/skills/pm/` をコミットし、CLAUDE.md に「機能追加・仕様変更時は pm スキルを使う」の1行を追記。`docs/decisions/` ディレクトリを作成。

## 5. 確定事項（2026-07-19 オーナー回答：「2択はより網羅的な方を優先」）

1. **スキルの厳しさ**: 仕様に触る変更は大小問わずすべて記録対象。文言・スタイル調整・バグ修正・リファクタのみ除外
2. **AppStore の前提**: Expo 前提の手順に加え、手段によらない汎用の審査知識も網羅
3. **農業ドメインの範囲**: 汎用の農業知識（法規・GAP・実務）を土台に、farm-app への適用を各節に併記
4. **意思決定ログの置き場**: `docs/decisions/` を新設（1変更1ファイル、YYYYMMDD-slug.md）

## 5.5 テスト結果（2026-07-19 実施）

計画どおり3本のテストプロンプトをスキルありで実行し、全て期待動作を確認：

1. **「収穫予測をAIで今すぐ」** → 実装に入らず、戦略順序（データ蓄積が先）を根拠に保留を推奨。代わりに安い布石（fields への面積カラム追加・reports.field の FK 化）を DB スキーマから自力で発見して提案。意思決定ログ＋再検討トリガー付き
2. **「土壌pHを必須化」** → 農業実務（pH測定は施肥時のみで頻度が低い→全報告必須化は虚偽入力を誘発しデータを汚す）を根拠に、施肥時のみのソフト必須を代案提示。App.tsx の実装箇所まで確認
3. **「AppStoreに出したい」** → WebView 不可・アカウント削除必須等のギャップをチェックリスト化し、TestFlight を中間目標にする二段構え（案B）を推奨。Apple Developer 登録など「今すぐやる3つ」も提示

いずれも「選択肢＋推奨」の形式・意思決定ログの生成・既存コードやスキーマへの接地ができており、フェーズ3は完了。今後は実運用の中で違和感が出た箇所を references に反映して改善する。

## 7. スキル分割と質の強化（2026-07-19 追記）

初版の `pm` スキルは PM プロセスと農業ドメイン知識を1つのスキルに同居させていたが、オーナーからのフィードバックで**システム/プロダクト設計の PM と農業ドメイン知識は別スキルに分けるべき**という指摘を受け、以下のとおり再構成した。

### 分割の理由
- 2つは性質が違う——PM は「何を作るか・作らないかの判断プロセス」、農業ドメインは「現場の事実知識」。同居させると、農業知識だけを単体で聞きたいとき（例：「南高梅の防除時期は？」）に PM の儀式が混ざってしまう
- 別スキルにすることで、それぞれ単体でも・組み合わせても使える。将来 farm-app 以外のプロジェクトに `agriculture` スキルだけ持ち出すことも可能になる

### 新構成

```
.claude/skills/pm/                       # プロダクト・システム設計のPM
├── SKILL.md
└── references/
    ├── workflow.md              # PMの仕事の進め方（課題定義・MVP・優先順位付け・スコープ管理・指標設計）
    ├── decision-frameworks.md   # 新規：JTBD/Opportunity Solution Tree/Kanoモデル/Cost of Delay・CD3/ICE/プレモータム
    ├── templates.md             # 意思決定ログ・ミニPRD・検証(実験)テンプレ・AppStoreチェックリスト・優先順位シート
    ├── appstore.md               # AppStore公開の要件・審査対策・Expo・リリース運用
    └── product-context.md       # farm-app固有のビジョン・優先順位基準・技術的制約

.claude/skills/agriculture/               # 農業ドメイン知識（新規スキル）
├── SKILL.md
└── references/
    ├── legal.md                 # 農薬取締法（義務）と帳簿記載（努力義務）を明確に区別、食品衛生法ポジティブリスト
    ├── cultivation.md           # IPM・施肥設計・果樹の年間サイクル（南高梅・温州みかんの栽培暦を具体例に）
    ├── certification-and-data.md # GAP認証比較(JGAP/ASIAGAP/GLOBALG.A.P.)、エコファーマー/有機JAS/特別栽培、WAGRI
    └── field-ux.md               # 圃場・作付けの概念、農家ユーザーの利用実態、記録データの資産価値
```

両スキルは `pm/SKILL.md` と `agriculture/SKILL.md` の双方に相互参照を明記し、分業関係（pmが判断、agricultureが知識提供）を維持している。

### PM スキルの質向上ポイント
- RICE/MoSCoW だけでは拾えない判断のために `decision-frameworks.md` を新設。要望を解決策から課題に戻す JTBD、解決策への恋を防ぐ Opportunity Solution Tree、機能の性質を見分ける Kano モデル、季節性のある farm-app に効く Cost of Delay/CD3、軽い日次判断用の ICE、実装前のリスク洗い出しであるプレモータムを追加
- `templates.md` の意思決定ログにプレモータム欄を追加、仮説段階の機能をいきなり本実装せず小さく試すための「検証（実験）テンプレ」を新設

### agriculture スキルの質向上ポイント（Web リサーチで裏取り）
- **義務と努力義務の峻別を明記**：農薬使用基準の遵守は法的義務、帳簿記載（5項目）は努力義務（罰則なし）——これを混同すると過剰な入力強制を「法律だから」と誤って正当化してしまうため、`legal.md` の最重要ポイントとして明記
- IPM（総合的病害虫・雑草管理）の考え方を追加し、「散布した記録」だけでなく「見送った判断」の記録価値にも言及
- 紀州の主要品目（南高梅・温州みかん）の年間栽培サイクルを具体例として追加（一般論に留めず、地域差がある旨も明記）
- GAP認証3規格（JGAP/ASIAGAP/GLOBALG.A.P.）の違い、エコファーマー・有機JAS・特別栽培の基準の違いを整理
- WAGRI（農業データ連携基盤）を将来の外部データ連携の選択肢として追加
- 農家ユーザーのUX実態に「代理入力（複数人で1つの記録を共有）」の観点を追加
