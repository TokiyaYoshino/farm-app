# PMスキル作成プラン

作成日: 2026-07-19 / 対象: farm-app（紀州農場アプリ）

## 1. 背景と目的

farm-app は思いつきベースで仕様変更が発生しており、以下のリスクがある。

- 仕様の一貫性が崩れ、AppStore 公開（審査・リリース計画）の障害になる
- 変更の「なぜ」が記録されず、後から判断の根拠を追えない
- ロードマップ（docs/roadmap.md）と実際の開発が乖離する

そこで **Claude が PM として振る舞うためのスキル**を作る。オーナー（吉野）に PM 知見がなくても、機能提案・仕様変更・リリース準備の場面で Claude が PM のプロセスを回してくれる状態がゴール。

## 2. スキルがカバーする3領域

| 領域 | 内容 |
|---|---|
| PMの仕事の進め方 | 仕様変更の受け止め方（Why の深掘り→影響範囲→優先順位付け→記録）、ミニPRD 作成、RICE/MoSCoW 等の優先順位付け、スコープ管理、意思決定ログ |
| 周辺知識 | AppStore 審査ガイドライン・公開準備（プライバシーポリシー、審査リジェクト典型例）、リリース管理・バージョニング、React Native/Expo 移行時の留意点（ロードマップの方向性に合わせる） |
| ドメイン知識（農業） | 農薬管理（希釈倍数・使用基準・農薬取締法）、防除記録・作業日誌の実務、圃場・作付けの概念、GAP 認証など記録が資産になる文脈、農家ユーザーの利用実態（屋外・片手・短時間入力） |

## 3. スキルの設計方針

### 置き場所と構成

リポジトリ内 `.claude/skills/pm/` に置く（farm-app 専用の文脈を含むため、プロジェクトスコープが適切）。1スキル + 参照ファイル構成（progressive disclosure）：

```
.claude/skills/pm/
├── SKILL.md                  # トリガー条件 + PMとしての基本動作（500行以内）
└── references/
    ├── workflow.md           # 仕様変更フロー・ミニPRDの書き方・優先順位付け手法
    ├── templates.md          # ミニPRD / 変更提案 / リリースチェックリストのテンプレ
    ├── appstore.md           # AppStore公開の要件・審査対策・リリース手順の知識
    ├── agriculture.md        # 農業ドメイン知識（農薬・防除記録・圃場・GAP）
    └── product-context.md    # farm-app固有：ビジョン、ユーザー像、ロードマップとの整合ルール
```

### スキルの中核動作（SKILL.md に書くこと）

ユーザーが「○○機能を追加したい」「ここの仕様を変えたい」と言ったとき、いきなり実装せず PM プロセスを挟む：

1. **Why の確認** — 誰のどの課題を解くのか、既存機能で代替できないかを1〜2問で確認
2. **整合チェック** — docs/roadmap.md のフェーズ設計・方針（「使い続けてもらえるアプリが最優先」等）と照合し、ズレていれば指摘
3. **影響範囲の評価** — DB スキーマ・RLS・既存機能・AppStore 審査への影響を列挙
4. **ミニPRD の記録** — `docs/decisions/` に軽量な意思決定ログ（1件=数十行）を残してから実装に入る
5. **ロードマップ更新** — 採用した変更は roadmap.md に反映する

ポイント：**重厚な PRD 文化を持ち込まない**。個人開発のスピード感を殺さない「数分で書ける記録」を徹底する。

### トリガー設計（description）

発動すべき場面：新機能の提案、仕様変更の相談、優先順位の相談、リリース/AppStore 公開の話題、「これ作るべき？」系の相談。
発動すべきでない場面：純粋なバグ修正、リファクタ、デザイン調整（既存仕様の範囲内の作業）。

## 4. 作成の進め方（skill-creator のループに沿う）

### フェーズ1: 要件確定（〜0.5日）
下記のオープンクエスチョンを確定（各項目にデフォルト案あり、そのまま採用でも進められる）。

### フェーズ2: ドラフト作成（〜1日）
- SKILL.md + references 5ファイルを執筆
- agriculture.md と appstore.md は Web リサーチで裏取り（農薬取締法の記録義務、App Review Guidelines の最新版）
- product-context.md は既存 docs（roadmap / db-schema / CLAUDE.md）から抽出

### フェーズ3: テストと評価（〜1日）
現実的なテストプロンプトでスキルあり/なしを比較し、eval viewer でレビュー：

1. 「収穫予測をAIでやる機能を今すぐ入れたい」→ ロードマップ長期フェーズとの整合指摘 + ミニPRD が出るか
2. 「作業報告の入力項目を変えたい（土壌pHを必須にする）」→ 影響範囲（DB・既存データ・UX）の評価が出るか
3. 「AppStoreに出すには何が必要？」→ 具体的なチェックリスト（プライバシーポリシー、審査対策、Expo化の前提）が出るか

### フェーズ4: 改善ループ
フィードバックを基に書き直し → 再テスト。満足したら description 最適化（トリガー精度の自動チューニング）を実行。

### フェーズ5: 導入
`.claude/skills/pm/` をコミットし、CLAUDE.md に「機能追加・仕様変更時は pm スキルを使う」の1行を追記。`docs/decisions/` ディレクトリを作成。

## 5. 確認したいこと（デフォルト案つき）

1. **スキルの厳しさ**: 仕様変更のたびに必ず記録を挟むか、大きい変更だけか。→ デフォルト案: DB スキーマや画面フローに触る変更は必須、文言・スタイル調整は不要
2. **AppStore の前提**: ネイティブ化は React Native/Expo で確定でよいか（appstore.md の内容が変わる）。→ デフォルト案: roadmap.md の記載どおり Expo 前提で書く
3. **農業ドメインの範囲**: 紀州農場で扱う作物・栽培方式に特化するか、汎用に書くか。→ デフォルト案: まず farm-app の既存機能（農薬・防除・圃場・収穫）に直結する範囲で書き、必要に応じ拡張
4. **意思決定ログの置き場**: `docs/decisions/`（1変更1ファイル） vs roadmap.md に追記のみ。→ デフォルト案: `docs/decisions/` を新設
