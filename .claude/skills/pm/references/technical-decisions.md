# システム・技術設計の意思決定

`workflow.md` と `decision-frameworks.md` は「何を作るか」の判断を扱う。このファイルは「**どう作るか**」——技術選定・アーキテクチャ・スキーマ設計といった、プロダクト機能の裏側にある構造的な決定を扱う。「システムやプロダクトの設計のPM」という役割の"システム設計"側の担当分。

機能追加の意思決定ログ（`templates.md` の1.）と何が違うか：意思決定ログは「何を・なぜ作るか」、ここで扱う ADR（Architecture Decision Record）は「どう実現するか、なぜその技術・構造を選んだか」。両者は独立に発生する——機能の意思決定ログから ADR にリンクすることもあれば、機能追加を伴わない純粋な技術判断（DB設計の見直し、ライブラリの乗り換え等）で ADR だけ書くこともある。

## 1. ADR を書くべき場面

次のいずれかに当てはまる技術判断は ADR として記録する（`docs/decisions/` に `YYYYMMDD-adr-<slug>.md` として保存し、機能の意思決定ログと区別する）：

- **後から覆すコストが高い決定**：DB スキーマの根幹（テナント分離の方式、主キー設計）、認証方式、ネイティブ化のフレームワーク（Expo 採用など）
- **複数の選択肢があり、選ばなかった理由を将来説明できないと困る決定**：ライブラリの選定、Supabase の使い方（RLS の設計方針）、状態管理の方式
- **CLAUDE.md の規約から逸脱する、または規約を新設する決定**：例えば「App.tsx の分割方針」を初めて決めるとき

逆に、日々の実装の中で閉じる技術判断（変数名、コンポーネント分割の細部）は ADR 不要。**「1年後の自分が『なぜこうなってるんだっけ』と聞かれて困るか」**が判断基準。

## 2. ADR-lite テンプレート

```markdown
# ADR: <決定の一言タイトル>

- 日付: YYYY-MM-DD
- 状態: 採用 / 見送り / 廃止（廃止時は後継ADRにリンク）

## 背景・コンテキスト
何を解決する必要があって、なぜ今この決定が必要か。1〜3行。

## 決定
何を選んだか。1〜3行。

## 検討した選択肢
| 選択肢 | 長所 | 短所 |
|---|---|---|
| 案A（採用） | | |
| 案B | | |

## 選定理由
なぜ案Aか。トレードオフの中で何を優先したか（3節の比較軸を使う）。

## 影響
- 変更・移行が必要な既存コード:
- 将来この決定を覆しにくくする要因（ロックイン）:

## 再検討のトリガー
どんな状況になったらこの決定を見直すべきか（例：ユーザー数がN件を超えたら、マルチテナント化が完了したら）。
```

## 3. 技術トレードオフの比較軸

技術選定で意見が割れたとき、次の軸で比較すると議論が具体的になる（全部を毎回埋める必要はない、効きそうな軸だけ選ぶ）：

- **学習・実装コスト**：今のスキルセット（Claude Code 併用の個人開発）でどれだけ早く形にできるか
- **保守性**：半年後の自分が読んで直せるか。個人開発ではここが特に重い——チームでのレビュー前提の複雑な設計は要らない
- **拡張性**：マルチテナント化・外部展開・AppStore 公開という既定路線に対して伸びしろがあるか
- **ロックイン**：後から乗り換えるコストの高さ（例：Supabase 依存度、Expo 採用後にネイティブへ逃げるコスト）
- **運用コスト**：金銭的コスト（従量課金の有無）、監視・障害対応の手間
- **farm-app の規模とのミスマッチ**：オーバーエンジニアリングの兆候（個人開発・ユーザー数十人規模の課題に対してマイクロサービス化のような重い解決策を検討していないか）を必ず自問する

**個人開発での基本方針**：保守性と実装コストを学習コストより優先する。複雑さは将来のマルチテナント化・外部展開が具体的に必要とするまで持ち込まない（YAGNI）。

## 4. farm-app の技術的負債と付き合う

`product-context.md` に記載の技術的制約（App.tsx への機能集中、RLS 確認必須、デザイントークン集約）は、いずれも「今は許容している技術的負債」。ADR を書く際に意識すべき原則：

- **負債を無自覚に増やさない**：大きめの機能を App.tsx に追加する提案が出たら、ロジック分離を一緣に検討する（強制はしないが選択肢として提示する）
- **負債の返済は機能追加とセットで**：負債単体の返済（リファクタのみ）は decisions の対象外（CLAUDE.mdの規約どおり）だが、機能追加のついでに関連箇所を整理するのは推奨——ADR の「影響」欄に書く
- **マルチテナント化中は特に慎重に**：新しいテーブル・カラムの設計は、テナント分離の方式と整合するかを ADR レベルで確認する

## 5. 非機能要件チェック（個人開発サイズでの簡易版）

大きめの技術決定の ADR には、次の観点を一言ずつ添えると後から見直しやすい。厳密な数値目標は個人開発では過剰なので、「問題ないか / 要注意か」の二値でよい：

- **パフォーマンス**：写真・音声メモなど容量の大きいデータの扱い（アップロード・表示速度）
- **セキュリティ**：RLS の抜け、権限のないユーザーが他農場のデータに触れないか（マルチテナント化中は最重要）
- **データ整合性**：意味を変える変更が過去データと接続を保てるか（`agriculture` スキルの `field-ux.md` 4節とも関連）
- **可用性**：Supabase・Vercel 側の障害時にどの機能が止まるか、許容できるか
