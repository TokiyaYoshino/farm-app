# AppStore 公開の知識

farm-app は現在 React (Vite) の Web アプリ。AppStore に出すにはネイティブアプリ化が前提で、ロードマップの方針どおり **React Native / Expo** 方向で書く。ただし審査・運用の知識は手段によらず共通なので汎用に整理する。

## 1. 公開までの全体像

1. Apple Developer Program 登録（個人 / 年 99 USD）
2. アプリのネイティブ化（Expo プロジェクト化）
3. App Store Connect でアプリ登録（Bundle ID、メタデータ、スクリーンショット）
4. TestFlight で内部テスト（審査なしで最大 100 人）→ 外部テスト（簡易審査）
5. 本審査提出 → 平均 1〜2 日、リジェクト時は修正して再提出
6. 公開（手動リリース / 段階的リリース選択可）

初回は登録〜公開まで**最低 2〜4 週間**見込む（リジェクト 1〜2 回を織り込む）。

## 2. 前提となる技術判断(Expo)

- **WebView ラッパーは不可**。既存 Web をそのまま WebView で包んだアプリはガイドライン 4.2（Minimum Functionality）でリジェクトされる定番パターン。審査では機内モードで起動されることがあり、白画面が出たら即アウト。React Native / Expo で UI をネイティブ実装し直すこと。
- Expo なら **EAS Build**（クラウドビルド、Mac 不要）と **EAS Submit**（App Store Connect への自動提出）が使える。個人開発では Mac・Xcode 管理の手間を大きく減らせる。
- Supabase クライアントは React Native でもそのまま使える。App.tsx のロジック層（Supabase 呼び出し・状態管理）と UI 層の分離を進めておくと移植コストが下がる——**ネイティブ化を見据えた仕様変更の判断材料**として覚えておく。
- 「iOS アプリである必然性」を作る機能（4.2 対策にもなる）：プッシュ通知（リマインダー）、カメラ直接起動（作業写真）、GPS（圃場位置）、オフライン入力。farm-app はいずれもロードマップと親和性が高い。

## 3. 審査リジェクトの主要因と対策

| ガイドライン | 内容 | farm-app での対策 |
|---|---|---|
| 2.1 完成度 | クラッシュ、バグ、プレースホルダ、審査員が機能に到達できない | ログインが必要なため**審査用デモアカウント必須**（管理者権限で全機能に到達できるもの）。空データだと価値が伝わらないのでデモデータも入れる |
| 4.2 最低限の機能 | Web サイトの焼き直し、機能が薄い | WebView 不可。プッシュ通知・カメラ・GPS などネイティブ機能を初回リリースに含める |
| 5.1.1 データ収集 | 収集データの説明不足、不要な権限要求 | 権限（カメラ・位置情報・マイク）の利用目的文字列を具体的に書く（「作業記録に写真を添付するため」等）。使わない権限は宣言しない |
| 5.1.1(v) アカウント | **アカウント削除機能がアプリ内に必須**（アカウント作成があるアプリ全て） | farm-app は管理者がアカウントを作る方式だが、削除導線は必要。Supabase 側の削除処理＋UI を用意 |
| 4.8 ログイン | サードパーティログイン（Google 等）を使うなら Sign in with Apple 併設 | 現状メール認証のみなら不要。将来 Google ログイン追加時は必須になる——**ログイン方式の仕様変更時はここを必ずチェック** |
| 2.3 メタデータ | スクリーンショットや説明文が実機能と不一致 | 「AI 予測」など未実装機能を説明文に書かない |

その他 2026 年時点で厳格化している点：プライバシー栄養表示の正確性、スパム的な類似アプリ判定。個人の実用アプリである farm-app は後者のリスクは低い。

## 4. プライバシー要件

- **プライバシーポリシー URL が必須**。収集データ（氏名、作業記録、位置情報、写真）、利用目的、第三者提供（LINE 通知、Supabase、Vercel）を明記。kishufarm.com 配下に静的ページで置けばよい。
- **App Privacy（プライバシー栄養表示）**：App Store Connect で収集データ種別を申告。実装と食い違うとリジェクト・公開後の摘発対象。位置情報・写真・ユーザー ID は申告対象。
- 将来の「データ販売」構想（ロードマップ長期）は、実行時にプライバシーポリシーと栄養表示の全面改訂＋ユーザー同意が必要になる。**データ活用系の仕様検討時は必ずこの観点を影響範囲に入れる。**

## 5. farm-app 固有の注意点

- **マルチテナント化との順序**：AppStore 公開は不特定多数への配布。現状の単一農場前提のまま出すか、マルチテナント化後に出すかは大きな分岐。「紀州農場専用アプリ」として限定公開する場合、Apple は特定組織向けアプリに Apple Business Manager での限定配布（Unlisted App / Custom App）という選択肢もある——一般公開前の中間手段として検討価値あり。
- **審査は仕様の一貫性を見る**：説明文・スクリーンショット・実装・プライバシー申告の 4 点が揃っている必要がある。仕様が頻繁に変わると、この 4 点の同期が崩れるのが典型的な事故。decisions のログはこの同期を保つための台帳でもある。
- 音声メモ（マイク）・写真・GPS と権限が多いアプリなので、権限要求のタイミング（初回起動で全部要求しない、使う場面で要求する）も審査・UX 両面で重要。

## 6. 提出とリリース運用

- **バージョニング**：マーケティングバージョン（1.2.0、semver 推奨）＋ビルド番号（提出ごとに増加）。Web 版と機能差が出るため、リリースノートで「アプリ版の変更」を明示する運用に。
- **段階的リリース（Phased Release）**：7 日かけて自動展開。初回は手動リリース＋様子見が無難。
- **審査の見込み時間**：通常 24〜48 時間。リジェクト対応も含めリリース希望日の 1 週間前提出を習慣に。
- TestFlight を「本番前の常設ベータ」として使い、作業者ユーザーに新機能を先行配布 → フィードバック → 本審査、の流れが farm-app の規模に合う。
