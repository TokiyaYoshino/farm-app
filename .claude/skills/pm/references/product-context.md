# farm-app プロダクトコンテキスト

PM 判断の拠り所となる farm-app 固有の前提。ここに書いてあることが docs/roadmap.md と食い違ったら **roadmap.md が正**（このファイルの更新を提案する）。

## ビジョンと戦略順序

**「入力データ蓄積 → 外部展開 → データ価値化」の順序を守る**（roadmap.md の方針）。

1. **今：入力データ蓄積** — 紀州農場で毎日使われ、記録が貯まり続ける状態を作る。短期の最優先は「使い続けてもらえるアプリ」＝入力継続率。
2. **次：外部展開** — マルチテナント化（進行中・最優先）が前提。他農場への展開、AppStore 公開はこの段階の手段。
3. **将来：データ価値化** — 分析・AI 予測・データ販売。蓄積と一貫性が原資。

この順序を飛ばす提案（例：データが貯まる前に分析機能を厚くする）は原則「保留」に振る。

## 優先順位の判断基準（上から強い順）

1. **入力の摩擦を減らす** — 報告 1 件の入力を速く・確実にする改善。最優先レーン。
2. **記録の法規・実務適合を保つ** — 農薬記録の主要項目（`agriculture` スキルの `legal.md` 参照）を欠かさない、データの意味を壊さない。
3. **外部展開の前提を整える** — マルチテナント化、認証・権限、ネイティブ化準備。
4. **閲覧・分析の充実** — データが貯まってから効く。急がない。
5. **収益化・データ販売** — 長期。今は仕様の布石（同意設計・データ一貫性)だけ意識。

## ユーザー像

- **管理者（吉野）**：経営視点。進捗・収穫実績・計画を見る。機能追加の発案者でもある——**発案者の欲しい機能と作業者の使う機能を区別する**こと。
- **作業者**：現場で入力する人。IT 習熟度に幅。入力の速さと分かりやすさがすべて。
- 利用環境（屋外・手袋・電波・繁忙期変動など）の詳細は `agriculture` スキルの `field-ux.md` を参照。

## 技術的制約（仕様判断に効くもの）

- `src/App.tsx` にほぼ全機能が集中（タブ state 切替、ルーターなし）。**画面追加のコストは低いが、App.tsx の肥大は将来のネイティブ移植コストに直結**。大きめの機能はロジック分離を併せて提案する。
- Supabase：テーブル変更時は **RLS ポリシー確認が必須**（CLAUDE.md 規約）。マルチテナント化中なので、新テーブル・新カラムはテナント分離の設計と整合させる。
- デザインは Soft Widget スタイル、トークンは `src/ui/tokens.ts` 集約。新画面の提案時はデザイン工数を「既存トークンで組める範囲か」で見積もる。
- デプロイは git push → Vercel 自動。Web 版のリリースコストはほぼゼロ、AppStore 版は審査コストが乗る（appstore.md）。

## 守るべき規約（CLAUDE.md より）

- 既存機能を削除しない（ナビから外しても tab コンテンツは残す）
- TypeScript の型を明示
- 仕様に触る変更はすべて docs/decisions/ に記録（本スキル導入により追加）

## 整合チェックの実務

新しい提案が来たら、このファイルの「戦略順序」「優先順位の判断基準」に当てて 1 行で判定する。例：

- 「収穫予測 AI を入れたい」→ 段階 3（データ価値化）の機能。今は段階 1。→ **保留を推奨**、ただし予測に将来必要なデータ項目が今の記録に欠けていないかだけ先に確認する（布石は安い）。
- 「音声入力を強化したい」→ 基準 1（入力の摩擦減）。→ **高優先で検討**。
- 「報告一覧に CSV 出力が欲しい」→ 基準 2（実務適合・出荷先への記録提出）に該当し得る。→ 用途を確認して優先度決定。
