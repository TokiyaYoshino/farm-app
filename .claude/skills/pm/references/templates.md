# テンプレート集

すべて「数分で書ける」ことを優先した軽量版。埋められない項目は「不明」と書いて先に進む（空欄より「不明と判断した」記録に価値がある）。

## 1. 意思決定ログ（docs/decisions/YYYYMMDD-<slug>.md）

仕様に触る変更すべてで作る。1 変更 1 ファイル。

```markdown
# <変更の一言タイトル>

- 日付: YYYY-MM-DD
- 状態: 採用 / 保留 / 見送り
- 種別: 新機能 / 仕様変更 / 削除・縮小 / リリース判断

## 課題（Why）
誰が・いつ・何に困っているか。1〜3 行。

## 決めたこと
何をどう変えるか。1〜5 行。縮小版を採用した場合はフル版との差分も。

## 検討した代替案
- 案 B: 〜 → 見送り理由
- 現状維持: → 見送り理由

## 影響範囲
- DB / RLS: 
- 既存機能: 
- AppStore / 法規: （該当なしなら「なし」）

## 過去の判断との関係
矛盾・上書きする decisions があればリンクと覆す理由。なければ「なし」。
```

## 2. ミニ PRD（大きめの新機能のとき。意思決定ログで足りない場合のみ）

意思決定ログの上位互換。画面が 1 枚増える規模以上の機能で使う。

```markdown
# <機能名> ミニPRD

- 日付 / 状態

## 課題と対象ユーザー
管理者 / 作業者のどちらの、どの場面の課題か。

## ゴールと非ゴール
- ゴール: この機能が成功したと言える状態（できれば指標つき）
- 非ゴール: 今回やらないと明言すること（Won't リスト）

## ユーザーストーリー
「<ユーザー>は<場面>で<操作>すると<結果>が得られる」を主要 3 本まで。

## スコープ（MoSCoW）
- Must / Should / Could / Won't

## 影響範囲・リスク
DB、RLS、既存機能、入力 UX、AppStore 審査、法規（農薬記録なら agriculture.md 参照）

## 検証方法
リリース後にどの数字・どの反応を見て成否を判断するか。
```

## 3. AppStore リリースチェックリスト（リリース判断のとき）

詳細な根拠は `appstore.md`。状況確認に使う短縮版：

```markdown
## 提出前チェック
- [ ] アカウント削除機能がアプリ内にある
- [ ] プライバシーポリシー URL（収集データと一致した内容）
- [ ] App Privacy（プライバシー栄養表示）の申告が実装と一致
- [ ] カメラ・位置情報・マイクの利用目的文字列（purpose strings）が具体的
- [ ] 審査用デモアカウント（全機能に到達できる権限）を用意
- [ ] クラッシュ・白画面なし（機内モードでの起動確認含む）
- [ ] 「iOSアプリである必然性」を説明できる（4.2 対策）
- [ ] スクリーンショット・説明文が実機能と一致
- [ ] バージョン番号・ビルド番号の採番ルールに従っている
```

## 4. 優先順位スコアシート（候補が 3 つ以上並んだとき）

```markdown
| 候補 | Reach(回/週) | Impact(0.25-3) | Confidence(%) | Effort(セッション) | RICE | 判断 |
|---|---|---|---|---|---|---|
| 音声入力改善 | 20 | 2 | 80 | 3 | 10.7 | 今期 |
```

スコアは根拠の説明用。最終判断は product-context.md の方針（入力継続率 > その他）が優先。
