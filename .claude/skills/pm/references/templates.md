# テンプレート集

すべて「数分で書ける」ことを優先した軽量版。埋められない項目は「不明」と書いて先に進む（空欄より「不明と判断した」記録に価値がある）。技術選定・アーキテクチャの ADR テンプレは `technical-decisions.md` の2節にある（機能の意思決定ログとは別物）。

## 1. 意思決定ログ（docs/decisions/YYYYMMDD-<slug>.md）

仕様に触る変更すべてで作る。1 変更 1 ファイル。

```markdown
# <変更の一言タイトル>

- 日付: YYYY-MM-DD
- 状態: 採用 / 保留 / 見送り
- 種別: 新機能 / 仕様変更 / 削除・縮小 / リリース判断

## 課題（Why）
誰が・いつ・何に困っているか。1〜3 行。

## 決めたこと
何をどう変えるか。1〜5 行。縮小版を採用した場合はフル版との差分も。

## 検討した代替案
- 案 B: 〜 → 見送り理由
- 現状維持: → 見送り理由

## 影響範囲
- DB / RLS: 
- 既存機能: 
- AppStore / 法規・農業実務: （該当なしなら「なし」。農薬記録・防除・GAP 等が絡む場合は agriculture スキルの知識を踏まえる）

## プレモータム（半年後に失敗していたとしたら、何が起きたか）
1〜3行。書けない場合はリスクを考え切れていないサイン（decision-frameworks.md 6節）。

## 過去の判断との関係
矛盾・上書きする decisions があればリンクと覆す理由。なければ「なし」。
```

## 2. ミニ PRD（大きめの新機能のとき。意思決定ログで足りない場合のみ）

意思決定ログの上位互換。画面が 1 枚増える規模以上の機能で使う。

```markdown
# <機能名> ミニPRD

- 日付 / 状態

## 課題と対象ユーザー
管理者 / 作業者のどちらの、どの場面の課題か。

## ゴールと非ゴール
- ゴール: この機能が成功したと言える状態（できれば指標つき）
- 非ゴール: 今回やらないと明言すること（Won't リスト）

## ユーザーストーリー
「<ユーザー>は<場面>で<操作>すると<結果>が得られる」を主要 3 本まで。

## スコープ（MoSCoW）
- Must / Should / Could / Won't

## 影響範囲・リスク
DB、RLS、既存機能、入力 UX、AppStore 審査、法規・農業実務（農薬記録・防除等が絡む場合は agriculture スキルを参照）

## 検証方法
リリース後にどの数字・どの反応を見て成否を判断するか。

## プレモータム
半年後に失敗していたとしたら、何が起きたか。1〜3行。
```

## 3. 検証（実験）テンプレ（仮説段階の機能・確信が持てない変更のとき）

「作ってから様子を見る」ではなく、**小さく試して確信度を上げてから本実装する**ときに使う。Opportunity Solution Tree（decision-frameworks.md 2節）の「検証」に対応。

```markdown
# 検証: <試すこと>

## 仮説
「〜すれば、〜という指標が、〜くらい動くはずだ」

## 最小の試し方
本実装せずに確かめる方法（例：既存画面に仮ボタンだけ置く、手動で1週間運用してみる、対象を数人に絞る）

## 判定基準
この数字・反応が出たら「本実装に進む」、出なければ「見送る」を事前に決める

## 結果と判断
実施後に追記。decisions ログに繋げる場合はリンクする。
```

## 4. AppStore リリースチェックリスト（リリース判断のとき）

詳細な根拠は `appstore.md`。状況確認に使う短縮版：

```markdown
## 提出前チェック
- [ ] アカウント削除機能がアプリ内にある
- [ ] プライバシーポリシー URL（収集データと一致した内容）
- [ ] App Privacy（プライバシー栄養表示）の申告が実装と一致
- [ ] カメラ・位置情報・マイクの利用目的文字列（purpose strings）が具体的
- [ ] 審査用デモアカウント（全機能に到達できる権限）を用意
- [ ] クラッシュ・白画面なし（機内モードでの起動確認含む）
- [ ] 「iOSアプリである必然性」を説明できる（4.2 対策）
- [ ] スクリーンショット・説明文が実機能と一致
- [ ] バージョン番号・ビルド番号の採番ルールに従っている
```

## 5. 優先順位スコアシート（候補が 3 つ以上並んだとき）

RICE（候補をまとめて比較する場面）。日常的な即答には decision-frameworks.md の ICE を使う方が軽い。

```markdown
| 候補 | Reach(回/週) | Impact(0.25-3) | Confidence(%) | Effort(セッション) | RICE | 判断 |
|---|---|---|---|---|---|---|
| 音声入力改善 | 20 | 2 | 80 | 3 | 10.7 | 今期 |
```

スコアは根拠の説明用。最終判断は product-context.md の方針（入力継続率 > その他）が優先。
